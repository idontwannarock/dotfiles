# Coordinating Lines

你不寫程式。你的產出是**裁決、跨線事實、handoff**。

這條 skill 是 [wayfinder](https://github.com/mattpocock/skills/blob/main/skills/engineering/wayfinder/SKILL.md)
的延伸。Wayfinder 規劃**一張決策地圖**並明說「**一個 session 只解一張票**」（research 除外）。
本 skill 處理它刻意排除的那半：**多條線同時在解票**，於是出現 wayfinder 沒有的問題
——票與票之間的合併順序、線與線之間的事實整合、以及誰有權推翻誰。

**本檔分兩層。** 主體（到〈與 {{ .n.devWorkflow }} 的關係〉為止）是**平台中立的協調原則**；
末尾的〈附錄〉收**平台與工具相依的機制**。附錄不是補充讀物，是主體的**前提**——
主體說「先讀再覆寫」，附錄才說在你這個工具上「讀」是哪一道指令。

## 先對齊：你已經有的東西就是 wayfinder 的東西

| wayfinder | 這裡的形式 |
|---|---|
| map issue | handoff 檔（`~/.agent/handoffs/<repo-slug>/`） |
| decision ticket | 一條線 ＋ 它的編號 |
| Decisions-so-far | handoff 的〈本輪產生的裁決（不要重新討論）〉 |
| Not yet specified（fog） | 〈待認領〉與〈Open / unresolved〉，**每項都要帶解鎖條件** |
| blocking relationships | 「解鎖條件：Ａ／Ｂ／Ｃ／Ｄ 全部合併」這種句子 |
| 用名字不用 ID | agent 用名字定址、handoff 用 slug 定址 |
| claim before work | `active_workflows.md` 那一列 |
| HITL vs AFK | 「要使用者裁決」vs「我自己判斷」 |

**fog 是一等公民。** 不知道的事要有名字、有住址、有「什麼時候可以變成票」的條件。
`「三分等 PM 裁決」` 是 fog；`「先照合理預設做」` 是把 fog 埋掉——**那是這條 skill 要防的頭號失敗**。

## 定址：一律用名字

**協調者的位址是名字（`coordinator`），不是 pane id。** 換手時 pane id 會變、名字不會。
交接＝舊的讓名，新的接走。

**接手後第一件事**：確認 agent 清單裡那個名字指著你自己，然後廣播一次。

**terminal title 不能拿來定址**——它是自動摘要，會過期又會撞名。
（實際的開線與改名指令見〈附錄 B〉。）

> **為什麼值得一條規則**：曾有協調者為了對一條線交接一件事，**連發三個 session 才找到對的**——
> 因為 terminal title 是自動摘要，當時它自己的 pane 標題與另一條 peer 線幾乎一字不差，
> 而且早就不是它在做的事。

## 跨線事實：這是協調者唯一無法外包的工作

**每條線只看得到自己那一面，合起來才是真相。** 沒有人在合，就沒有人知道真相。

> **2026-08-21 的實例。** 同一份「有幾條讀端點會落後」的清單，三條線各報一個數字：
> dev 上實測 **8** 條、Ｃ 線修掉一條變 **7**、Ｂ 線新增兩條報 **10**。
> **三個都對，三個都不是要發給前端的那個數字。** 合併後是 **9**。
> 任何一條線單獨發通知都會發錯。

推論出來的規則：

- **收到回報先問「它是站在哪個版本上量的」。** peer 給的狀態幾乎一定過期——
  它量的時候是真的，你讀到的時候基準已經動了。
- **把合併後的結果寫回每一條相關的線**，不要只寫進文件。線不知道別條線改了什麼。
- **正本只有一份。** 決定哪份檔案是正本並告訴所有線；其餘的指回正本，
  不要各自維護一份會分岔的副本。

## 不要照單全收下游的結論

**線會報錯，而且錯得很有說服力**——它們拿著真實證據，只是前提過期或範圍不對。

2026-08-21 一天之內被推翻三次，每次都是好事：

- 前任協調者說 Ａ 線會產生「第九條 stale 端點」→ Ａ 線指出那條端點**本來就在清單裡**，
  變的是同一條端點裡哪個**欄位**落後
- Ｃ 線提醒「量測 map 少了新端點」→ 查證後是**按端點記的**，沒有那個缺口
- **協調者自己**查到一個 CLI 旗標就宣布「手機那面解決了」→ Ｂ 線查證後推翻：
  那個旗標只作用在本機終端機

**最後那則是最重要的一則**，因為它反過來：

> **協調者給的問題框架本身可能是錯的。**
> 我問了一個三選一，而正確答案在三個選項之外。
> 下游若只回答框內選項，錯誤會被放大成決策。

所以派問題時**明確授權對方推翻前提**：「如果我問的框架不對，直接說框架不對。」

**推廣**：`--help` 說某個旗標「設 display name」時，要問的是「**誰的** display」。
一個旗標的文件說它做什麼，沒說它的作用範圍到哪。

## 排程：合併位是稀缺資源

**前提**：以下規則假設 repo 的合併方式**不保留 merge commit**（例如 fast-forward ＋ 一律 squash）。
在那種 repo 上，**主線一動，所有開著的 MR/PR 立刻需要 rebase、綠燈作廢，
而且已掛上的自動合併會被一起取消**（不是保留著等你 rebase）。
若你的 repo 允許 merge commit，下面前兩條的急迫性會大幅下降，第三、四條仍然成立。

- **沒有使用者可見效果的改動不跟有效果的線搶合併位。** 判準不是「改動大不大」，
  而是「它防的失敗是吵的還是靜默的」——fixture 一改就整支測試紅，那是債不是事故，可以排隊。
- **不要讓兩條 MR/PR 同時掛自動合併等佇列決定順序。** 那不是佇列，是「誰先合，其餘全部掉出來」。
  **明確指定誰先合**（挑 pipeline 最短、改動面最小的），其餘的**先不要 rebase**，
  等它進去之後一次到位。
- **「先不要動」常常比「立刻動手」省。** 省下來的是整輪 CI，不是幾分鐘。
- **rebase 零衝突不等於語意相容。** 點名對方動過哪些檔案，要線逐處對過。

（自動合併與 pipeline 狀態的查法見〈附錄 C〉。）

## 收尾：四個訊號，而且要你自己驗

一條線說「做完了」不是收尾條件。**四個獨立訊號**，缺一不可：

1. MR/PR 已合併（查平台上的狀態，不是查回報）
2. handoff 已在 `archive/`
3. worktree 已處置、branch 已刪
4. `active_workflows.md` 那一列已移除

**你要自己查，不是信回報。** 回報是線的視角，可能漏、可能過期。

**外加一個只能問、查不到的第五項：「你實際用到哪一號、有沒有可回收的？」**

配給一條線的編號區間（decision 編號、migration 版本、任何預先切給它的號段），
**配出去不等於用完**。而沒用完的那幾號**在任何檔案裡都不存在**——
grep 不到、配額表只記得配了多少，**只有線自己知道**。

> **回收有一個時間窗，錯過就永久浪費。** 線收工之後就沒人記得了。
> 2026-08-21 實例：一條線配到 D294、實際只用到 D292，**主動回收了 D293／D294**。
> 若只讀配額表，下一條線會從 D295 起，那兩號永久蒸發。

所以編號對帳要**三邊都問**：`grep`（會低估也會高估）、配額表（會高估已用量）、
**以及線本身**。前兩者查得到，第三者只能在它還活著的時候問。

**合併驗證不要用 `git branch -d`**——squash 讓它對「已合併」與「真的沒合併」給同一個答案。用 scoped diff：

```bash
paths=$(git diff --name-only $(git merge-base origin/<base> <branch>) <branch>)
git diff origin/<base> <branch> -- $paths   # 要是 0 bytes
```

**四訊號齊了才關 pane。** 一段 handoff 一個 session，收尾**之後**才有權關
——那是「不要關別人 tab」的明示例外，但授權範圍是「收尾後」。
**關 tab 前先查 tab 裡有幾個 pane**，別的線可能跟它同住。

> **「一段 handoff 一個 session」的完整形狀**：一個任務因 context 撐不住而需要多次 handoff，
> 或一個 handoff 任務做完了——兩種情形處置相同：**指揮該 session 收尾 → 關掉它 → 用新 handoff 開新 session**。
> 長壽 session 累積的是無人讀得到的 scrollback，不是資產。
> 這條規則的安全性**完全押在「收尾」是真的**：關之前先問「這個 session 知道而檔案不知道的，是什麼？」
> **協調者自己也適用，而且最容易漏**——它是最長壽的那個。

## 交付物不要留在會消失的地方

**scratchpad 隨 session 消失。** 協調者的產出（對外文件、待認領清單、跨線盤點）
一產出就移到活得比 session 久的地方——`~/.agent/handoffs/<repo-slug>/attachments/`。

2026-08-21：前任協調者的對外文件留在它自己的 scratchpad，pane 關掉前搶救才沒丟。

**引用要用它未來的路徑。** handoff 被歸檔後路徑會變成 `archive/<ID>.md`，
所以在還活著的檔案裡引用它時，直接寫歸檔後的路徑。

## 整份覆寫之前先讀 —— 這一族的失敗全部靜默

**對「共寫、且沒有版控」的東西做整份覆寫，是本 skill 裡最反覆出現的一種事故。**
2026-08-21 一天之內三起，形狀完全相同：

| 覆寫的動作 | 蓋掉了誰 | 怎麼被發現的 |
|---|---|---|
| 未錨定的 `sed` 改 `active_workflows.md` | 另一條線的進度列 | 對方主動回報 |
| 沒先讀就整份寫入一份已存在的檔案 | 另一條線剛寫的內容 | 對方主動回報 |
| 清空 agent 的輸入框 | **使用者未送出的草稿** | **沒有被發現** |

**前兩起靠對方回報才浮出來。第三起的當事人是人，而人不會回報**
——他甚至不知道自己的輸入消失過。

> **受害者是人的那一格最危險，而它剛好是最容易被當成「清一下殘留」的那一格。**
> 另外兩格的受害者是 agent，會回報；人不會。**風險最高的動作看起來最無害。**

所以規則不是「小心一點」，是機械的：

- **整份或整段替換（`sed`、覆寫式寫檔、清空輸入框），動手前一定先讀**
- 改共寫檔的某一列，用**名稱錨定**並斷言「恰好命中 1 列」才寫檔
- **判斷不出那段內容是誰留的，就不要覆寫**——留著的成本遠低於蓋掉
- **蓋掉之後要留痕跡。** 這一族之所以危險不是因為蓋錯，是因為**蓋了沒人知道**。
  若已經蓋掉且事後才察覺，**主動告知當事人**，不要用「結果沒壞」自我赦免
  ——結果沒壞是運氣，而當事人有權自己判斷。

## 共寫檔：平行寫會靜默重複，不會衝突

`active_workflows.md`、共用筆記、盤點表都是共寫的。**append 一節永遠成功，沒有任何警告。**

- 改自己那列要用**名稱錨定**，並斷言「恰好命中 1 列」才寫檔
- 寫一則**已存在**的筆記前先 `grep` 標題關鍵字，不要只看索引（索引會落後）
- 發現重複時**收掉自己那塊、併進證據較具體的那節**，並標明哪句是誰實測的
- **同一則檔案的更新只指派給一條線**——「順手記一下」正是相撞的來源

## 認得「複寫了別處的事實」這一族

協調者橫跨多條線，所以看得到單一條線看不到的**同型缺陷**。最常見的一族是：
**某處複寫了另一處的事實，而來源改動時，複寫的那份不會知道。**
失效一律是**靜默**的——沒有編譯錯誤、沒有測試轉紅、只有一個看起來仍然正確的答案。

2026-08-21 在四條不同的線上各出現一次，形狀完全相同：

| 複寫的那份 | 來源 | 來源改了會怎樣 |
|---|---|---|
| 兩處寫死的 `SEEDED_EVENTS = 5` | fixture 檔的事件筆數 | 加一筆事件，兩個 `5` 都不會編譯失敗，四處斷言**一起**變成錯的期望值 |
| 架構文件裡的容忍前提 | 實際的 migration 策略 | 一步到位 DROP 踩掉前提，文件仍宣告舊保證 |
| 盤點表的「未移植」兩列 | 端點實際狀態 | 端點移植了，記載變成錯的，沒有東西會紅 |
| 某條決策裡的「目前沒有別的 caller」 | 程式碼現況 | 下一個人加一個 caller，那句話悄悄不成立 |

**協調者要做的兩件事：**

1. **一條線報上來的「我發現一處註解／記載是錯的」，先問它是不是這一族。**
   若是，修那一處只是治標——要問的是「**還有誰複寫了同一個事實**」。
2. **修法的判準是「讓它去數，不要讓它記」。** 把兩處複寫合成一處共用常數**看起來**已經修好了，
   但來源一改它照樣錯。**去重不是目的，免疫於來源漂移才是。**
   （對文件而言的等價做法：不是刪掉那句話，是註明它的已知例外並指向正典。）

> **這條判準也適用於本檔自己。** 一份跨 repo 的 skill 若把某個 repo 的編號、
> 某個平台的設定、某個 agent 的旗標抄進正文，它就是這一族——換掉底層之後靜默失效。
> 所以那些東西全部集中在〈附錄〉並標明前提，而不是散在主體裡。

## 反模式

- **把 fog 埋成合理預設。** 不知道的事要有名字和解鎖條件，不要用預設值蓋掉。
- **輪詢 CI。** 平台支援自動合併就掛上去，然後在 rebase 後重掛一次並查一次。那一次查不是恢復輪詢。
- **替線做決定卻不說理由。** 線會照做，然後在下一輪用錯誤的理由推廣它。
  裁決要帶「為什麼」與「什麼條件下會翻案」。
- **自己動手寫程式。** 你一旦開始改 code，就沒有人在合併跨線事實了。
- **只讀公開討論串。** 關鍵定案常在 DM／私訊，只讀公開串會讀出相反的結論。
- **在所有線都合併前發對外通知。** 數字會變。

## 與 {{ .n.devWorkflow }} 的關係

`{{ .n.devWorkflow }}` 是**一條線內部**的流程（grill → spec → implement → verify → review → merge）。
本 skill 是**線與線之間**的角色。兩者不重疊，但要接得上：

- 被協調的線在 {{ .n.devWorkflow }} 的 **{{ .n.finishBranch }} 階段**要回報四訊號給 `coordinator`
- 線在任何階段撞到**跨線事實**（別條線也會動到的檔案、共用的量測、編號衝突）要立刻回報，不要等收尾
- 線收到裁決時，**若覺得前提不對就推翻它**，不要只在給定選項裡挑

# 附錄：平台與工具相依的機制

**這裡的每一節都帶前提。** 前提不成立時，該節不適用，但主體的原則仍然成立。

## 附錄 A：herdr —— 跟線互動的機制

> 前提：以 [herdr](https://github.com/) 這類 agent 多工器管理各線的 pane。
> `herdr agent start --kind` 支援 21 種 agent（`pi`／`claude`／`codex`／`gemini`／`cursor` 等），
> 協調機制本身與 agent 種類無關。

### 輸入框非空時不要送 —— 這條是無條件的

`herdr agent prompt` 會把你的文字**接在輸入框既有內容後面**一起送出。所以在非空的輸入框上送，
**送出去的是一則沒有人寫過的合併訊息**：收訊方分不出邊界在哪，而殘留文字的作者
**從未同意在這個時刻、這個脈絡下送出它**。

**這一點與那段文字是誰留的無關。** 就算確定是 harness 補的、確定不是任何人的意圖，
串起來送仍然是錯的——你送出的東西不是你寫的，也不是它寫的。

所以順序是：**先把輸入框處理乾淨，再送你自己的文字。** 不要讓 `prompt` 去 append。

**「是誰留的」只決定你怎麼清空它，不決定你可不可以串著送**：

| 來源 | 特徵 | 怎麼清空 |
|---|---|---|
| 自己上一則的回聲、殘渣 | 認得出是自己寫的 | `send-keys <name> ctrl+u` 清掉 |
| **agent harness 產生的建議** | **內容剛好是「下一步顯然該做的事」** | 不是任何人的意圖，清掉 |
| 使用者親手打的草稿 | **帶有現場推不出來的資訊** | **不要清也不要送**——去問使用者 |
| **判斷不出來** | — | **去問使用者**。他是唯一的 oracle，成本是零 |

判準：一段文字若**剛好就是任何人看了現場都會說的下一句**，很可能是 harness 補的；
人打的字通常帶有現場推不出來的資訊。

**讀與送必須是兩次獨立動作。** 把 `read` 與 `prompt` 寫進同一道指令，
讀的輸出確實產生了，但**沒有任何時刻能消費它**——防線就退化成儀式。
先讀、看過、決定，才送。

> **2026-08-21 實例甲：三方同時誤判。** 一條線的輸入框裡有「繼續，跑第 2 組」，
> 前任協調者、接任協調者、以及那條線本身**三方都判定那是使用者未送出的草稿**，於是三方都不碰。
> 結果那條線空等了一個永遠不會來的 enter，還把「waiting on you to send …」寫進 recap 當**目標狀態**。

## 附錄 B：開線與命名

**名字要符合 herdr 的 `[a-z][a-z0-9_-]{0,31}` 且在活著的 agent 之間唯一。**
慣例是**用 change 名稱**，協調者固定叫 `coordinator`。

```bash
herdr agent start <name> --kind {{ .n.agentKind }} --pane <pane-id>
```

{{ if eq .n.tool "claude" -}}
**名字有三層，最容易搞錯的是第二層到不了手機。**

| | 設定方式 | 誰看得到 |
|---|---|---|
| **herdr 定址名** | `herdr agent rename <pane> <name>` | 只有 herdr（`agent list` 的 name 欄、`agent prompt <name>`） |
| **本機 display name** | `claude -n <name>`（啟動）或 `/rename <name>`（跑到一半也能改） | prompt box、`/resume` picker、terminal title——**全部都是本機終端機** |
| **Remote Control session 名** | `claude --remote-control [name]` | **claude.ai 與手機 app**（唯一到得了那裡的一層） |

開線時一行讓三層同名：

```bash
herdr agent start <name> --kind claude --pane <pane-id> -- --remote-control "<name>" -n "<name>"
```

herdr 把 `--` 之後的參數原樣透傳給 agent，於是同一個字串貫穿三層。

**已經在跑的 session 補不了 `--remote-control`**（那是啟動旗標，橋接要在 session 建立時做）。
只能用 `/rename` 釘死本機那層，手機那層**從下一批新線開始**。

> **`--remote-control` 是行為改變，不只是加一個旗標**：session 會被橋接到 claude.ai，
> 對話內容、檔案路徑、程式碼片段都經過那邊。內部程式碼的專案要先確認這個代價可接受。
{{- else -}}
**這個 agent 沒有「啟動時設定 session 名稱」的旗標**，也沒有等價於 Remote Control 的
遠端 session 名稱層。**只有 herdr 定址名這一層**，用上面那道指令設定即可。

需要讓使用者在別處分辨各線時，靠 herdr 的名字與 pane 標題，不要假設有第二、三層。
{{- end }}

## 附錄 C：合併平台的行為

> 前提：repo 不保留 merge commit（fast-forward ＋ 一律 squash），且平台提供
> 「pipeline 成功後自動合併」。GitLab 的 `merge_method=ff` ＋ `squash_option=always` 是這種組合。

- **主線前進的那一刻，平台會「取消」已掛上的自動合併**，而不是保留著等你 rebase 完再繼續。
  所以每次 rebase 之後要**重掛一次，然後查一次確認它真的回來了**。那一次查是唯一該查的時點。
- **force-push 之後，pipeline 狀態會有一段時間指著舊 commit 的成功紀錄。**
  判準要寫成兩件事而不是一件：**先確認 pipeline 指的 sha 對得上本地 HEAD，然後才看它的狀態**。
  順序不能反——狀態單獨看永遠有答案，而那個答案可能是上一輪的。
- **要查一個 MR/PR 為什麼合不進去，看平台的詳細合併狀態欄位。**
  陷阱：**Draft 狀態會蓋掉 CI 的阻擋原因**——是 Draft 時它一律回報 draft，即使 pipeline 是紅的
  也看不到 CI 的那一條。要驗證 CI 閘門有沒有生效，**必須先撤 Draft**。
