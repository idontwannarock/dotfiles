# Coordinating Lines

你不寫程式。你的產出是**裁決、跨線事實、handoff**。
**這不是分工偏好，是容量問題**——你一旦開始改 code，就沒有人在合併跨線事實了。

這條 skill 是 [wayfinder](https://github.com/mattpocock/skills/blob/main/skills/engineering/wayfinder/SKILL.md)
的延伸。Wayfinder 規劃**一張決策地圖**並明說「**一個 session 只解一張票**」（research 除外）。
本 skill 處理它刻意排除的那半：**多條線同時在解票**，於是出現 wayfinder 沒有的問題
——票與票之間的合併順序、線與線之間的事實整合、以及誰有權推翻誰。

**本檔分兩層。** 主體（到〈與 {{ .n.devWorkflow }} 的關係〉為止）是**平台中立的協調原則**；
末尾的〈附錄〉收**平台與工具相依的機制**。附錄不是補充讀物，是主體的**前提**——
主體說「先讀再覆寫」，附錄才說在你這個工具上「讀」是哪一道指令。

## 先對齊：你已經有的東西就是 wayfinder 的東西

**fog 是一等公民。** 不知道的事要有名字、有住址、有「什麼時候可以變成票」的條件。
`「三分等 PM 裁決」` 是 fog；`「先照合理預設做」` 是把 fog 埋掉——**那是這條 skill 要防的頭號失敗**。

你已經有的載體，對得上 wayfinder 的每一格：

| wayfinder | 這裡的形式 |
|---|---|
| map issue | **裂成兩個載體**：handoff 檔（`~/.agent/handoffs/<repo-slug>/`）＋〈map〉——多條線帶進了拓撲，而拓撲不屬於任何一個 session，塞不進任何一份 handoff |
| decision ticket | 一條線 ＋ 它的編號 |
| Decisions-so-far | handoff 的〈本輪產生的裁決（不要重新討論）〉 |
| Not yet specified（fog） | 〈待認領〉與〈Open / unresolved〉，**每項都要帶解鎖條件** |
| blocking relationships | 「解鎖條件：Ａ／Ｂ／Ｃ／Ｄ 全部合併」這種句子 |
| 用名字不用 ID | agent 用名字定址、handoff 用 slug 定址 |
| claim before work | `active_workflows.md` 那一列 |
| HITL vs AFK | 「要使用者裁決」vs「我自己判斷」 |

## 定址：艦隊限定的名字

**協調者的位址是 `<fleet>-coordinator`，不是 pane id、也不是光禿禿的 `coordinator`。**
`<fleet>` 是這支艦隊開場時選定的前綴，線一律叫 `<fleet>-<change>`（命名規則見〈附錄 B〉）。
換手時 pane id 會變、名字不會；交接＝舊的讓名，新的接走。

**為什麼不能是固定字串**：herdr 的名字是**整台機器一個扁平命名空間**，
且在活著的 agent 之間唯一。固定叫 `coordinator` 等於宣告全機只能有一支艦隊。撞上了有兩種形狀：

| 發生方式 | 後果 |
|---|---|
| 兩支艦隊同時跑 | 後來的搶不到名字；而它派出的線契約上仍寫著 `coordinator`，**回報投給先搶到的那一支** |
| 先佔用的那支退場 | 名字被釋放、由後來者接走，**原本那批線的回報自此全部改道** |

⚠️ **這不是解析失敗。** 唯一性約束**保證**那個名字解得開——投遞端不報錯，
收訊端讀到的是一則格式正確、署名也正確的回報。與〈誰有資格說這句話〉同一族：**下游分辨不出來。**
所以「沒人回報投錯」不能當作沒發生過。

### 兩道檢查，兩個維度

**前綴分艦隊，cwd 分 repo。兩者正交，少任何一道都有一整類撞法漏掉。**

| 檢查 | 分得出什麼 |
|---|---|
| **前綴**(`<fleet>-`) | **哪一支艦隊**——同一個 repo 內也分得出 |
| **cwd** | **哪一個 repo** |

**前綴是慣例，cwd 是機械後盾。** 派線訊息可能漏給位址、可能過期，
已經在跑的線也不會回頭改名——那時擋得住誤投的只有 cwd 這一道。`herdr agent list` 每筆都有 `cwd`：

| 端 | 檢查 | 不符時 |
|---|---|---|
| 你要定址一條線**之前** | ①名字以 `<fleet>-` 開頭 ②它的 `cwd` 與你在同一個 repo | **不投遞**，先查清楚它是誰 |
| 你**收到**一則回報 | 署名的那條線在**你的名冊上** | **不處理**，退回並告訴對方投錯了 |

只驗投遞端擋不住別支艦隊投進來的東西，只驗收報端擋不住你自己打擾別人。**兩端都要。**

⚠️ **前綴那一項不能省。** 同一個 repo 底下可以有第二支艦隊（見〈資源池〉），
**它的 cwd 會跟你完全一樣** —— 只比 repo 的話，打錯字的同 repo 位址會整個通過。

⚠️ **`cwd` 不等於 repo 路徑。** 被協調的 repo 常是 bare ＋ worktree 佈局，
線的 cwd 是 worktree 路徑，與主 checkout 沒有共同前綴。
判準是「同一個 repo 的工作樹範圍內」，**不要拿 repo 路徑做字串前綴比對**，
而且要拿**對方的** cwd 去算，不是在你自己的目錄下跑一次。
（怎麼算、以及三個會靜默出錯的寫法，見〈附錄 B〉。）

### 艦隊名冊：herdr 答得出「在」，答不出「應該在」

**維護一份名冊，記這支艦隊該有哪些 session。** 落點見〈附錄 B〉。

**為什麼不能只靠 `herdr agent list`**:`herdr agent` **沒有任何 history 子命令**，
而名字在 agent 退出時就被清除。所以**已死的 session 與從未存在的 session 完全無法區分**——
**herdr 只有「在」，沒有「應該在」，缺席在它眼裡永遠不是異常。**
一條線 crash、被誤關、或在協調者換手時被漏掉，就這樣無聲消失。

**名冊記什麼，判準是「這條線的 session 被換掉時，這一格會不會變」：**

| 記 | 不記 |
|---|---|
| 名字（`<fleet>-<change>`） | status、pane id |
| **啟動形狀**：kind ＋ 角色 ＋ 該不該帶旗標 | **`cmdline` 字串** |
| **指派的工作樹** | 跑到第幾步、tasks n/m |
| 這條線是幹嘛的（change 名稱） | 換過幾手 |

⚠️ **記「啟動形狀」，不是 `cmdline` 原文。** `cmdline` 是 **per-process 事實**，
交接換了 process 就變——它正是本表左欄判準要排除的那種欄位，記進來就是在帳本裡塞一格鏡子。
而它宣稱的用途（事後查得到某個 session 當初怎麼被開出來）本來就兌現不了：
**旗標欄位對「協調者」與「路人」給同一個答案**，它沒有資格區分這兩者（見〈第二種形狀〉）。
**重開一條線需要的是形狀，不是原文。**

⚠️ **記「指派的工作樹」，不是從清單觀測到的 `cwd`。** pane 的 cwd **跟著 `cd` 走**，
而線可能從主 checkout 起手、之後才開 worktree。拿過期的落點重開，
**會在錯的工作樹上開出一條名字完全正常的線**。重開之前再與 `active_workflows.md` 的落點欄核對一次。

⚠️ 右欄那些是 `active_workflows.md` 的欄位。抄進來就是〈複寫了別處的事實〉——
**名冊只留「把不見的那個重開起來」所需的最小集合。**

**名冊與 `herdr agent list` 的差集就是偵測器：**

| 名冊有 | herdr 有 | 判讀 |
|---|---|---|
| ✅ | ✅ | 正常 |
| ✅ | ❌ | **漏掉了／被關掉了** → 拿名冊上的工作樹 ＋ **啟動形狀**原地重開 |
| ❌ | ✅ | 不屬於本艦隊（就是〈第二種形狀〉那個「第三態」） |

**第三列補掉了「三態使分母不可知」的一半**——分母不可知是因為沒有分子，**名冊就是分子**。

⚠️ **協調者自己也在名冊上。** 少了那一列，第三列會把**你自己**判成「不屬於本艦隊」；
更要命的是**協調者猝死將永遠不可偵測**——線猝死偵測得到（它的列還在），
而偵測這件事本身是由死掉的那個東西執行的。兩者不對稱沒有理由。

**寫入有三個時機**：開艦隊時建協調者那一列、派線時增線的一列、**線在語意上退出艦隊時**刪一列
（刪列掛在〈收尾〉那份清單上）。自我交接時**名冊一列都不用改**。

⚠️ **沒有並行 append 的理由是「寫入者只有協調者一個」，不是「時機只有兩個」。**
時機的數量是手段，而手段會變——它在補上協調者那一列的那一刻就從二變成三了，
而承重的那一半（單一寫入者）一格都沒動。**拿手段當理由的規則，會在手段改變時無聲失效。**

⚠️ **理由是「形狀不得變」，不是「名字沒變」。** 名字沒變這個理由對已經過期的 kind
與旗標欄同樣成立——它解釋不了那兩格為什麼還是對的。**真正的理由是下一節那條規則。**

⚠️ **行程意外死亡不刪列。** 那一列留著正是偵測器要的：重開之後兩邊又都在，警報自動解除。
**只有「這條線不再屬於這支艦隊」才刪。**

### 交接必須同形狀

**交接 ＝ 照名冊那一列的啟動形狀原地重開。形狀不得變。**
要換 kind 或換旗標**就不是交接**，是「這條線收掉、協調者重新派一條」——
而重新派線就是**派線**，走既有的寫入時機。

**三個理由：**

1. **旗標由角色決定，不由 session 決定。** 線一定要帶關閉發問管道的旗標、協調者一定不能帶
   （見〈第二種形狀〉）。交接改掉它**不是一個要被記錄的新事實，是一個 bug**。
2. **保住「協調者是名冊唯一寫入者」。** 讓接班者自己改那一列就是加第二個寫入者，
   而〈整份覆寫之前先讀〉記著同一天三起，**前兩起靠對方回報才浮出來**。
   ⚠️ 反對的理由是**多一個寫入者**，不是「多一個時機」——時機現在就有三個（見上一節），
   而協調者自己執行的時機再多也不會多出寫入者。
3. **與〈艦隊名冊〉裡「記指派的工作樹，不記觀測到的 `cwd`」那條 ⚠️ 同一把尺。** 那一格已經在同一條軸上裁決過：
   名冊記**指派值**，不記觀測值。kind 與旗標套同一把尺，答案自己掉出來。

**這條規則課給前任，在讓出名字之前指路——指路，不搬資料。**

> **前任 SHALL 在讓名之前，於交接文件寫下一句：接班者要以**名冊那一列**的形狀開出來。
> SHALL NOT 把 kind 與旗標的值複製過去。**

理由與〈第二種形狀〉那條同構：**「你必須保留發問能力」只約束得到現任**，
現任讀它的時候接班人還不存在——所以責任要放在**還存在的那一方**。
而前任要提供的不是資料，是**一個指標**：執行重開的那個人需要被告知去讀哪一列。

⚠️ **不要用「前任是唯一知道自己 argv 的人」立論——那個理由已經死了。**
名冊記的是**指派的形狀**，不是**觀測到的 argv**，而形狀由角色決定。沒有人需要前任的 argv。
只指路換來三件事：不與附錄 B 那條「不要把形狀值抄一份到 handoff」相斥、**不需要優先權規則**（名冊是唯一權威，
兩份資料才需要決定誰贏）、而且 handoff 那支 skill 不必為此新增欄位。

⚠️ **這條只能在讓名那一刻防，事後稽核不出來。** 名冊 ∩ herdr 的差集在交接後兩邊都在，
一律判「正常」——**形狀錯了偵測器不會轉紅**。所以下一節那道自檢是必要的第二道，
而不是多餘的例行公事。**不要為此再補一個測不準的稽核 gate**——理由見〈自檢與稽核〉。

### 鏡子與帳本

**一份資料該不該落檔，先問「有沒有一個更新的權威來源」。有，就別鏡像它。**
`:167` 那次把某條線的基底與 tasks n/m 抄進 map，就是這樣被外部檢視當場抓到的。

**但「查得到現在」不等於「查得到應該」** —— 只列活體的來源答不出缺席，那一格必須自己記。
名冊之所以不算鏡子，就在這裡：它與 `herdr agent list` 答的是不同的問題，**交接時只有後者變**。

⚠️ 別拿機器層的 workflow 登錄檔類比——**那種檔案記的是推導不出來的 per-machine 路徑映射，
不是 live 狀態的鏡像。**

### 接手後第一件事

**其中「啟動形狀」那項線與協調者都要做，「讀 `msgs/`」那項也是**——其餘只有協調者做。
⚠️ **線的接班人一定要讀**：裁決與合併後的跨線事實**正是寫給線的**，
而引用義務掛在「下一則回報」上。**交接若發生在那則回報之前，接班人根本不知道有裁決存在**
——而它的名字、它的工作樹、它的一切看起來都完全正常。

**逐條核對：**

1. agent 清單裡 `<fleet>-coordinator` 這個名字指著**你自己**，且 `<fleet>` 與 handoff 裡
   繼承來的那個**相同**——前綴是前任的裁決，不是你重新選的
2. **你的啟動形狀對不對**——查你自己的 process cmdline（不經顯示層的證據），
   與名冊那一列的形狀比對：kind 對不對、**該不該帶那個旗標、實際帶了沒有**。
   **不符時的處置依你的角色而定，見下表**
3. **讀 `msgs/` 自上次交接以來的內容**——那是你唯一能繼承「送出了什麼、什麼還沒被處理」的地方。
   ⚠️ 少了它，這條協定買到的可重讀性**剛好在最需要兌現的那一刻沒有兌現**：
   前任的裁決正本躺在那裡，而你不知道它們存在。
4. 廣播一次

**「啟動形狀」那項少了會怎樣：你會在第一次需要升級到真人時才發現升級鏈斷了**，
而那時你手上多半已經有一條線停在那裡等你。

**不符時的處置依角色分流：**

| 你是 | 處置 |
|---|---|
| **線** | **具名回報協調者**（升級契約本來就含「並停下」，見〈派線時關掉線的發問管道〉） |
| **協調者** | **立刻對使用者說，並請使用者依名冊那一列的形狀重開**——kind 與旗標**兩格都要**，不是只講「沒帶旗標」 |

⚠️ **協調者不要「回報協調者」——那是你自己。** 而且接班協調者的失效態**正是升級鏈已斷**：
它是唯一該升級到真人的角色，被誤帶旗標時它沒有上級可報。

⚠️ **請求重開時要把形狀的兩格都講出來。** 形狀有 kind 與旗標兩格，而你查的也是兩格；
只說「重開一個沒帶旗標的 session」在 **kind 錯而旗標對**的情況下會重開出同樣錯的 kind——
於是自檢每次都報同一件事，而處置每次都修不到它。

⚠️ **名冊上沒有你這一列，本身就是一個 finding。** 要回報，**不要當成「沒事可查」**——
差集表第三列會把沒有列的活體判成「不屬於本艦隊」，而那個判讀對你自己是錯的。

⚠️ **偵測並回報，不是偵測並自行代償。** 發現不符時 **不要**自己想辦法繞過，
**不要**去改設定檔補旗標——那是啟動旗標，跑到一半補不回來，而且寫進設定檔會一起關掉別人
（三個層級各會關掉誰，見〈派線時關掉線的發問管道〉）。**自行代償正是本檔的頭號失敗：
「命名了 fog 但照走預設值」。**

**兩個半邊，補救方式不同：**

| 半邊 | 交接後補得回來嗎 | 補救 |
|---|---|---|
| **旗標**（機械保障） | **補不回來**（啟動參數） | 依上表分流，由收到的那一方決定要不要重開 |
| **升級契約**（行為約束） | **補得回來**（prompt 層） | 協調者直接重發，不必重開 session |

⚠️ **「實際帶了沒有」這一問依 kind 而定。** 只有部分 kind 有關掉發問管道的機械手段
（對照表見〈附錄 B〉，其餘 kind **目前未知／多半沒有**）。在沒有機械手段的 kind 上，
這一問**顯性退化**：說出「這個 kind 沒有機械手段，所以只驗得到 kind 與角色」，
**不要靜默通過**——否則「不適用」與「檢查過了沒問題」讀起來一模一樣。

**契約才是承重的那一半。** 2026-08-21 的 A/B 實測裡**兩組都沒有發問工具**，
唯一變數是有沒有契約，而無契約那組照樣挑了版本號往下走（實測全文見〈派線時關掉線的發問管道〉）。
所以線發現自己少了旗標時，正確反應是**確認契約在不在**，而不是繞過或停擺。

⚠️ **但那次實測沒有涵蓋這個情境，這一步是外推。** 實測的兩組**都沒有工具**；
而「少了旗標」的線是**有**工具的。實測證明的是「無工具時契約就夠」，
**沒有證明「有工具時契約仍然夠」**——真正想擋的誘惑（手上有選單，直接問使用者）
在那次實驗裡根本不存在。所以契約在的時候行為**多半**是對的，
但這是推論不是量測；**撞到時照樣回報，不要拿這一段當放行的依據。**

⚠️ **這道自檢取代不了〈交接必須同形狀〉那條指路義務。兩者一個是預防、一個是偵測。**

| | 它做什麼 | 少了它會怎樣 |
|---|---|---|
| **指路**（前任讓名前） | 讓重開這個動作**一開始就對** | 旗標錯了只能事後發現，而那時**補不回來** |
| **自檢**（接班者上任） | 驗**重開已經發生之後**的結果 | 沒有任何東西會轉紅——差集表對兩邊都在的名字一律判「正常」 |

**不要寫成「前任交代防前任沒交代」**——一條義務防不了它自己被略過，那是套套邏輯。

### 自檢與稽核

**自檢可行，稽核不可行——而理由不是你以為的那個。**

⚠️ **不要用「第三方不知道每個 session 的角色」立論。那個理由已經被名冊本身推翻了：
名冊記的正是「誰該是什麼角色、該不該帶旗標」，它就是第三方原本缺的那一欄。**

**真正擋住稽核的是另一件事：herdr 的名字與 process 之間沒有可靠的 join。**
`agent list` 給 `cwd`，**不給 pid、也不給啟動參數**；而要稽核就得對每一個名字找到它的 process
再去讀旗標。2026-08-21 那次實測裡角色是**靠人知道的**，同一次掃描還有四個 session
的角色無法從 argv 判定——缺的是那道 join，不是那一欄資料。

**自檢不需要那道 join**：你讀的是**你自己的** cmdline，join 由「你就是你」免費提供。

⚠️ **這條禁令綁在那道 join 上，不是綁在「稽核本質上不可能」。**
herdr 哪天給得出 name→pid，這條就該失效並重新評估——**不要把它留成一條沒有人記得為什麼的永久禁令**。
（依 repo 的 `context/principles.md`「限制要寫在它真正的成因那一層」：從機制反推的限制，機制一改就無聲失效。）

**terminal title 不能拿來定址**——它是自動摘要，會過期又會撞名。
（實際的開線與改名指令見〈附錄 B〉。）

> **為什麼值得一條規則**：曾有協調者為了對一條線交接一件事，**連發三個 session 才找到對的**——
> 因為 terminal title 是自動摘要，當時它自己的 pane 標題與另一條 peer 線幾乎一字不差，
> 而且早就不是它在做的事。

## 跨線事實：這是協調者唯一無法外包的工作

**每條線只看得到自己那一面，合起來才是真相。** 沒有人在合，就沒有人知道真相。

- **收到回報先問「它是站在哪個版本上量的」。** peer 給的狀態幾乎一定過期——
  它量的時候是真的，你讀到的時候基準已經動了。
- **把合併後的結果寫回每一條相關的線**，不要只寫進文件。線不知道別條線改了什麼。
  ⚠️ 這句的意思是「**不要只寫檔而不通知**」，不是「不要寫檔」——**合併值屬於第三格：檔案 ＋ 通知，兩個都要**
  （判準見〈線與線之間的每一則往來都要選載體〉，不在這裡重寫）。**只通知不寫檔，接手的人重驗時就沒有原文可查。**
- **正本只有一份。** 決定哪份檔案是正本並告訴所有線；其餘的指回正本，
  不要各自維護一份會分岔的副本。

> **2026-08-21 的實例。** 同一份「有幾條讀端點會落後」的清單，三條線各報一個數字：
> dev 上實測 **8** 條、Ｃ 線修掉一條變 **7**、Ｂ 線新增兩條報 **10**。
> **三個都對，三個都不是要發給前端的那個數字。** 合併後是 **9**。
> 任何一條線單獨發通知都會發錯。**上面三條就是從這裡推出來的。**

> ⚠️ **常見的做錯法：在所有線都合併前就發對外通知。** 數字會變——這則軼事就是它的代價。

**「你是量的還是記的？」** 一條線回報「我照規則做了」時，問它是**去量了**還是**引用記憶**。
引用記憶的結論換一台機器、換一個環境就失效；量到的是當下的事實。
派工時就要求後者：「**請附上你量到的值，不要只說你遵守了。**」

> **2026-08-21 實例。** 規則是「codegen 要用拋棄式 DB，不要用共用 DB」。那條線沒有用
> 「我記得要用拋棄式的」交差，它去量了共用那台停在哪一版——**落後三支 migration**。
> 於是那條規則從一段警語變成一個數字。而污染不只是「混進別條線的表」，
> 也可能是「**少了幾支 migration 的**表」——**後者更陰險，產出的程式碼會編譯、會過測試。**

**而這條規則會反過來咬你自己。** 「某條線有沒有動某個檔案」是**查得到**的事：

```bash
git diff --stat <base> <head> -- <path>
```

憑記憶、憑該線的自述、憑「它的任務範圍應該不包括那裡」都會漏。而且**兩種保證的強度不同**：

| 你的答案 | 對什麼問題安全 |
|---|---|
| 「**沒碰**那個檔案」 | 任何問題 |
| 「碰了，但**沒碰你在乎的那一段**」 | **只有那一個問題** |

下游若問的是另一段而拿到前者的答案，**它會被誤導，而且不會知道要自己去驗**
——你的回答聽起來已經蓋掉了整個檔案。**協調者犯這個錯比線貴：你的答案會被多條線當成跨線事實採信。**

> **2026-08-21 實例。** 協調者寫「Ｄ 線**沒有動** `fixtures/qa-run.sql`，所以你的盤點仍然成立」。
> 那條線去跑了 `git diff --stat`：**動了。** 結論對，理由錯——盤點成立的原因是
> 「碰了、但改的是另一筆 INSERT」。

**還有一種跨線事實不是數字，是「兩邊各自正確，組合出第三個效果」。** 見〈共寫檔〉末尾。

## map：線與線之間的那一格

**map 只放線與線之間的東西**：拓撲、互斥的資源、合併值。**它與艦隊同生同滅。**

**map 是工作面，不是知識庫。** wayfinder 的 map issue 也一樣——一個 feature 的 issue，做完就關掉。
所以 map **不會**被升進 repo 層的長青 context：「Ａ 線現在卡著 Ｂ 線」是小時級變動的東西，
放進一個要走 review 的長青載體，第一天就腐爛。
**工作面會死，殘留的原則不會死，兩者不該同層**——可重用的殘留走既有的晉升閘門，
與一次性設計決策同一條路。
**一條線自己的狀態（分支、基底、tasks n/m、下一步）指回 `active_workflows.md`，不要抄進 map。**

⚠️ **所以 map 不能收進 workflow 目錄。** 它明文要求線的狀態**指回** `active_workflows.md`，
代表它**站在那些 workflow 之上、跨越多個 workflow**——收進去是**降一層**，
而且會讓那個目錄名說謊：叫 workflow 的地方裝著一個不屬於任何單一 workflow 的東西。

因為你已經有兩個載體，而三者答的是不同的問題：

| 載體 | 它答的問題 |
|---|---|
| handoff 目錄 | **有哪些事** |
| `active_workflows.md` | **誰跑到哪一步** |
| **map** | **這件事在哪、卡著誰、誰卡著它** |
| **`fleet.md`** | **這支艦隊該有哪些 session，以及不見的那個怎麼重開** |

**handoff 目錄是一堆各自獨立的檔案；map 是一個有拓撲的物件。** 看到「都是待辦載體」就判定重複，
漏掉的正是那張圖本身。

> **2026-08-21：協調者當場犯過，由外部檢視抓到。** 它把某條線的
> 「基底 `526ffcd`、tasks 6/24、第 2 組尚未開始」整段抄進 map 的線表。
> **那正是〈複寫了別處的事實〉**——來源一動，map 不會知道，而且不會有任何東西轉紅。

### wayfinder 四格之外要加兩格，而且它們性質相反

| 格子 | 性質 | 少了會怎樣 |
|---|---|---|
| **資源佔用登記處** | **互斥**——誰佔了別人不能用 | migration 版號對撞（rebase 零衝突，啟動才炸） |
| **跨線量測** | **分歧**——三個都對，要的是合併值 | 8／7／10 三個數字都對、都不是要發出去的那個 9 |

**混成一格的具體害處**：會讓人以為「報了數字」就等於「認領了」。

⚠️ **這一格只有在「這個池只有你一個仲裁者」時才有意義。**

> **一支艦隊必須完整擁有它所仲裁的稀缺資源池。兩支艦隊不得共用同一個池。**

合併位、migration 版號、編號區間、`active_workflows.md`、影響半徑重疊的檔案——這些綁的是 repo，
不是艦隊。**兩支艦隊共用一個池 ＝ 兩個仲裁者管同一批號碼 ＝ 沒有人在仲裁**，
而**兩邊各自的登記處都會顯示乾淨**，因為它們互相看不見。
那正是下面那個 8／7／10 的形狀：**兩份都對，合起來錯。**

⚠️ **而艦隊限定的名字讓這件事更難被發現**——訊息不再交錯了，
**而訊息交錯原本是撞號唯一會露出來的地方**。隔離之後，衝突要等到合併才炸。
**所以這條不是「最好有」，是必須有。**

**合法的例外**：兩支艦隊打不同的 base branch，合併位就是兩個池。
但 **base branch 分開不代表整個池分開**——migration 版號通常仍是同一條全域遞增序列。
**逐項問「這一項資源，兩支艦隊會不會爭」，不要整包判。**

**資源格至少三欄：配了什麼／目前用到哪／已回收。**
少第三欄，沒用完的號段**在線收工那一刻永久蒸發且 grep 不到**。

### 寫入權要分開，不能都歸協調者

理由是〈共寫檔〉那節：平行 append 永遠成功、沒有警告，**所以格子的所有權要能對應到誰有權改哪一列。**

| 內容 | 誰寫 | 為什麼 |
|---|---|---|
| Destination／Out of scope／解鎖條件 | **只有協調者** | 那是裁決 |
| 資源格的「目前用到哪／已回收」 | **線自己** | 只有它知道 |
| 跨線量測的原始值 | 線，**且註明站在哪個 commit 上量的** | 換個基底就是另一個數字 |
| 跨線量測的合併值 | 協調者，**且標明那是合併值** | 免得被當成某條線的原始回報 |

**更新的強制點比 wayfinder 多一個。** wayfinder 是「解一張票更新一次」；艦隊要多一個：
**線在 rebase 或被搶先合併之後**。那正是「你量的數字站在哪個版本上」失效的時刻，
**而且是事後才知道的事**——等線自己想起來，那一輪已經浪費掉了。

⚠️ **這一族最該被點名的是 map 自己。** 它明寫「任何線都可以追加」，
而它整場都是協調者在做整檔 read-modify-write。受害者會是那條剛追加完的線，**而它不會知道。**
修法見〈整份覆寫之前先讀〉的三層。

## 不要照單全收下游的結論

**線會報錯，而且錯得很有說服力**——它們拿著真實證據，只是前提過期或範圍不對。

2026-08-21 一天之內被推翻三次，每次都是好事：

- 前任協調者說 Ａ 線會產生「第九條 stale 端點」→ Ａ 線指出那條端點**本來就在清單裡**，
  變的是同一條端點裡哪個**欄位**落後
- Ｃ 線提醒「量測 map 少了新端點」→ 查證後是**按端點記的**，沒有那個缺口
- **協調者自己**查到一個 CLI 旗標就宣布「手機那面解決了」→ Ｂ 線查證後推翻：
  那個旗標只作用在本機終端機

**最後那則是最重要的一則**，因為它反過來：

> **協調者給的問題框架本身可能是錯的。**
> 我問了一個三選一，而正確答案在三個選項之外。
> 下游若只回答框內選項，錯誤會被放大成決策。

所以派問題時**明確授權對方推翻前提**：「如果我問的框架不對，直接說框架不對。」

**推廣**：`--help` 說某個旗標「設 display name」時，要問的是「**誰的** display」。
一個旗標的文件說它做什麼，沒說它的作用範圍到哪。

### 方向不只一個，而漏掉的那個發生得更頻繁

上面三則全是「**協調者 ← 線**」。實際上還有兩個方向：

**① 後任 ← 前任。** 交接是**唯一一次**有人帶著新鮮眼睛重讀前任全部結論的時刻，
所以**接手不是「照著做」，接手包含「重驗你要繼承的結論」。**
`pickup` 的〈動工前重跑 `git fetch`〉是這條規則在事實層的形態，這裡把它推廣到結論層。

> **2026-08-21 實例。** 新任協調者上任第一件事就推翻前任那條「某旗標解決了手機那面」的結論。
> ⚠️ **前任的「我搞砸了」也要重驗，而且更少人去查**——去查像是在替自己開脫。
> 那則「協調者清掉了使用者草稿」的自責，事後查證是誤判（見附錄 A 實例丙）。
> **handoff 會把未經查證的自責原樣搬給下一個人，而下一個人沒有現場可以查。**

**② 否定斷言 ← 一個看不見佇列的視野。** `grep` 型的**否定**斷言
（「零讀取端」「沒有別的 caller」「沒有人動這個檔」）**對佇列裡開著的 MR/PR 是隱形的**。

> **2026-08-21 實例。** 一條線在某個 commit 上 grep 出「某欄位讀取端只有三處」，
> 據此寫進 design 說「移除之後沒有任何端點回報它」。**而另一支 MR 當時已經開著，正要新增第四個讀取端。**
> 它的 grep 沒有錯——**它證明的是「在我這個 base 上沒有」。**

- **否定斷言要嘛連同「已對過當時開著的 N 個 MR/PR」一起報，要嘛請你確認。**
  **肯定斷言不受影響**——「有三處在用」不會因為別人加了第四處而變假。
- **你這一側要主動比對合併佇列，不要只採信。**

**而通則比「佇列」寬：**

> **斷言一件事之前，先確認自己讀的是**能回答它的那個東西**。**

同一條線在**相反方向**也錯過一次：它宣告「移除後三個 Scenario 會失去唯一的觀察點」，
**漏看了實現那些 Scenario 的測試**——那些測試本來就直接讀投影欄，從未經過端點。
**Scenario 的文字不指定觀察點，觀察點只存在於實現它的那支測試裡。**
佇列與測試只是兩個具體的「那個東西」。

⚠️ **你要記的一面**：**一條線往「風險被高估」方向的自我更正，比往嚴重方向的更難出現**
——沒有人會因為風險被高估而受害，所以沒有壓力去查。

## 證據的資格：這個東西有沒有資格回答你的問題

**這一節防的失效與〈跨線事實〉不同。** 那裡的失效是**取到錯的值**；這裡的失效是
**這個東西根本不回答你的問題，而它的措辭聽起來像在回答**。
**後者防不了的話，前面所有的合併都是在合併垃圾。**

### 四層，而且是遞進的

| 層 | 要問的 | 防的漏 |
|---|---|---|
| ① | 這個欄位對「是」與「否」兩種輸入會不會給出**不同**的答案？ | 顯示欄位沒資格當證據 |
| ② | 這個檢查**在什麼情況下會紅？做給我看。** | 檢查根本不會紅 |
| ③ | 你注入的**真的是一個差異**嗎？ | 示範本身是 no-op |
| ④ | 它比的東西**涵蓋了交付物的全部**嗎？ | 覆蓋範圍的漏 |

**①**：對同一個答案的欄位，**不管它的措辭聽起來多像在回答你的問題**，都不能拿來區分那兩種輸入。
決定性反例的形狀值得記：**找一個已知為否的樣本，看那個欄位對它說什麼。**
可用的證據是**不經過顯示層**的那種：process command line、檔案內容、HTTP 狀態碼。

> ⚠️ **常見的做錯法：只讀公開討論串。** 關鍵定案常在 DM／私訊，
> **只讀公開串會讀出相反的結論**——那是同一族：拿一個對「有沒有別的定案」給不出答案的來源當證據。

> **2026-08-21：同一天在同一個題目上錯三次**（兩次判成「已解決」、一次判成「沒生效」），
> 方向不同、成因完全相同——**拿一個不是為這個問題設計的顯示欄位當證據**。
> 決定性反例出現時才解開：一個**已知沒有帶那個旗標**的 session，兩個顯示欄位對它的答案
> 與帶旗標的那個**一字不差**。

**②③**：把主觀判斷換成機械檢查是對的，但**「必須零差異」不是一條完整的驗收條件**。

> **2026-08-21 實例。** 裁決是「兩邊各套一個空 DB，schema diff 必須零差異」。
> 那條線去校準時發現：**第一版通過了偽陽性測試，而通過的原因是兩邊的 dump 都是空的**
> ——`mysqldump` 在該環境下被禁用，**它先把前言寫進 stdout、才在 stderr 報錯退出**，
> 留下一份**非空、看起來正常**的檔案。
>
> **一個永遠輸出空字串的工具，在「比較兩份相同的東西」這項測試上是滿分。**
>
> ⚠️ 而它「做給你看」的那次示範裡，四項注入有一項是 **no-op**——把某欄位從 `as_cs`
> 「改成」`as_cs`。**一個假的注入配上一個壞掉的檢查，會互相掩護成一次成功的示範。**

**④ 最難，因為①②③都會過。** 一個只比 schema 的檢查真的會紅、注入也是真差異，
**它只是沒有看那一半**——某支 migration 有一筆 seed `INSERT`，而 `--no-data` 看不見它。
**schema 等價 ≠ 交付等價。**

⚠️ **每加一層守衛就多一個沒人守的最外層**，所以規則不是無限往外推，是
**把最外層放在人看得懂、且會被逐條核對的地方**。而「放在交付物裡」還不夠：

> **一個教訓寫在散文裡與寫在清單裡，對讀者的效果不同，
> 但對寫的人而言感覺一樣「已經寫了」。**

**驗收一條規則時不要問「你寫了嗎」，要問「它在哪一節？那一節會被逐條核對嗎？」**
散文段落、括號、附註、`> 引言` —— 這些位置的內容在覆核時會被略讀。

### 紅燈的歸因：紅的那幾支，是為了你的理由紅的嗎？

> **探針要單獨改變你主張的那一個變因；它若順帶改變別的，紅燈就不再指向你的主張。**

> **2026-08-21 實例。** 要證明「四處測試複寫了 fixture 的事件筆數」，探針是往 fixture 加一筆事件。
> **但隨手加一筆會同時弄紅可產出性測試**——那種紅**看起來也像成功的紅燈**，
> 它證的卻是「fixture 不再可被產生」。正解是挑一筆**對其餘一切惰性**的探針：
> 掛在不存在的聚合 id 上、沒有任何推導路徑會取用、不動相關 stream 版本。

### 失敗的計數可以證明盤點的完整性

一份唯讀盤點只能證明「**我找到的都在這裡**」，證不了「**沒有我沒找到的**」。
但紅燈那一步的**失敗支數**剛好證得了後者：**恰好四支紅、其餘 443 支全綠**
——**紅的若是五支或三支，盤點就有漏或有誤。**

**驗收一份盤點時不要只問「你怎麼找的」，問「有沒有一個動作，它的結果會在你漏掉東西時不一樣？」**
那才是完整性的證據，而不是搜尋方法的自述。

### 取得嚴謹度的方法是守衛，不是告誡

> **一條抽象的規則說「要小心」；一個擋著你的守衛讓你不小心就過不去。**

所以**這是一個動作，不是一句提醒**：動手前先問
**「這個 repo 裡有誰會因為我這個探針而不高興？」**——那些會不高興的東西**就是探針的規格說明書**。
**「沒有人會不高興」不是安全訊號，是「沒有東西在守這一格」的訊號。**

反過來用：要一條線做出你要的嚴謹度時，**與其在指令裡多寫一段規則，
不如問「有什麼東西會在你做錯時擋住你？沒有的話先做一個」。**

### 一個永遠有答案的讀取，答案可能屬於上一個時刻

①問的是「這個欄位分不分得出是與否」；這一條問的是「**這個答案屬於哪一個時刻**」。
三個載體不同、機制相同的實例：

| 讀到的東西 | 它其實屬於 |
|---|---|
| pipeline 狀態 | 上一個 commit（force-push 後） |
| `git status` 乾淨 | 「還沒被搬」的那一刻 |
| 一個 idle pane 的畫面快照 | 上一次重繪（見附錄 A） |
| **你對 `<fleet>-coordinator` 這個名字提問得到的回答** | **當下那一任**——而你不會知道那是第幾任 |

**規則：先確認答案屬於哪一個時刻，再看它的內容。** 順序不能反——內容單獨看永遠有答案。

⚠️ **最後那一列的受害者是「你問的那個人是誰」。** `<fleet>-coordinator` 是名字不是 session
（〈定址〉那節寫著），所以**同一個問題在今天不同時刻問，會得到不同任的答案，而回答者不會提醒你**。

> **2026-08-21 實例：本檔的作者自己犯的。** 起草時去問「你這個 session（第四任）手上有沒有某個工具」，
> 對方是**第八任**，而問題所指的那件事是**第六或第七任**做的、pane 已被現任親手關掉。
> **提問要把時間或 pane 釘住，或者接受答案只對當下有效。**

## 排程：合併位是稀缺資源

**明確指定誰先合，其餘的先不要動。** 合併位一次只有一個，而每一次主線前進都會讓其餘所有線付一輪 CI。

> **前提**：以下規則假設 repo 的合併方式**不保留 merge commit**（例如 fast-forward ＋ 一律 squash）。
> 在那種 repo 上，**主線一動，所有開著的 MR/PR 立刻需要 rebase、綠燈作廢，
> 而且已掛上的自動合併會被一起取消**（不是保留著等你 rebase）。
> 若你的 repo 允許 merge commit，下面前兩條的急迫性會大幅下降，第三、四條仍然成立。

- **沒有使用者可見效果的改動不跟有效果的線搶合併位。** 判準不是「改動大不大」，
  而是「它防的失敗是吵的還是靜默的」——fixture 一改就整支測試紅，那是債不是事故，可以排隊。
- **不要讓兩條 MR/PR 同時掛自動合併等佇列決定順序。** 那不是佇列，是「誰先合，其餘全部掉出來」。
  **明確指定誰先合**（挑 pipeline 最短、改動面最小的），其餘的**先不要 rebase**，
  等它進去之後一次到位。
- **「先不要動」常常比「立刻動手」省。** 省下來的是整輪 CI，不是幾分鐘。
- **rebase 零衝突不等於語意相容。** 點名對方動過哪些檔案，要線逐處對過。
- **狀態條件不要寫成時序條件。** 兩者只在該狀態**尚未成立**時一致。

> **2026-08-21 實例（協調者犯，線抓到）。** 派下的順序是
> 「兩道 review → 修 → **等 CI 綠** → 掛自動合併」。**CI 當時已經是綠的。**
> 真正的約束在別處：**review 若有發現、推了新 commit，綠燈與自動合併會一起作廢**，
> 所以正確形式是「**review 全部收斂、確定不再推 commit 之後才掛自動合併**」。
>
> **同族**：「佔位的是**已領走的號**，不是**開著的 MR**」——
> **約束寫的是狀態，判斷那個狀態要看的東西卻另有其物。**

（自動合併與 pipeline 狀態的查法見〈附錄 C〉。）

## 收尾：一份清單，而標「你自己查」的那些不能靠回報

一條線說「做完了」不是收尾條件。**清單上每一項都缺一不可**，而**標「只能問」的那些性質不同**：

⚠️ **下表的符號只是呈現順序，不是身分。** 指涉某一項時用它的**內容**命名（「編號回收」「名冊列移除」），
**不要寫「第五項」**——插入一項就會讓所有指涉它的文字同時變假，**而且沒有任何東西會轉紅**。

| | 項目 | 誰來取得 |
|---|---|---|
| ① | MR/PR 已合併（查平台上的狀態，不是查回報） | **你自己查** |
| ② | handoff 已在 `archive/`，**或這條線從未產生 handoff——要明說是後者** | **你自己查** |
| ③ | worktree 已處置、branch 已刪 | **你自己查** |
| ④ | `active_workflows.md` 那一列已移除 | **你自己查** |
| ⑤ | **`fleet.md` 那一列已移除**——這條線在語意上退出艦隊了 | **你自己查** |
| ⑥ | **你的 `msgs/` 裡有哪些該活過艦隊？搬去哪了？**（handoff／memory／`attachments/`）**或這條線一則訊息都沒送過——要明說是後者** | **只能問，查不到** |
| ⑦ | **你實際用到哪一號、有沒有可回收的？** | **只能問，查不到** |
| ⑧ | **還有什麼只有你知道？** | **只能問，查不到** |

**標「你自己查」的那些你要自己查，不是信回報**——回報是線的視角，可能漏、可能過期。
**標「只能問」的那些查不到，而它們有時間窗：線收工之後就沒有人知道了。**

> **名冊那一列只在這裡刪，不要在別的地方刪。** `fleet.md` 那一列是「這條線該存在」的唯一記錄，
> 而**行程意外死亡時它必須留著**——留著才叫得出「有一條線不見了」。
> **只有語意上的退出（收尾、取消）才刪列。** 把「意外死了」跟「不再屬於這支艦隊」混為一談，
> 就等於把偵測器關掉。

> **搬移那一項為什麼是「只能問」。** 它的謂語是「**該**活過艦隊的」——那是內容判斷，**沒有載體可查**。
> 空的 `msgs/`、內容確實不需要留的 `msgs/`、該搬而沒搬的 `msgs/`，**三者在檢視下完全一樣**。
> 而同樣形狀的「編號回收」本來就在這一半：**同形狀不同欄位，那是分類錯誤。**
> （判準是本節自己那條：**有沒有那個載體，不是有沒有做那個動作。**）
>
> `msgs/` 與艦隊同生同滅——**拆艦隊就是刪掉一個目錄**，而那正是這條協定買到的乾淨。
> 代價是：**沒搬走的東西跟著一起消失，而失敗是靜默的**——目錄刪掉之後，沒有任何人會知道少了什麼。
> **這與「線收線前交出的知識」是同一族**，只是這次執行刪除的是**我們自己排的動作**。
> ⚠️ **搬完之後，引用要用它搬移後的路徑**，與 handoff 歸檔那條規則同一條：
> 寫在還活著的檔案裡的引用，若指著即將消失的位置，**它會在建立引用的同一步就壞掉**。
>
> ⚠️ **但這一項只掃得到「這條線的」訊息。** `msgs/` 裡還有不屬於任何單線的東西——
> 協調者的廣播、合併後的跨線事實，以及**每一則裁決**。那些由下一節的拆艦隊清單負責。

### 拆艦隊之前：這份清單的擁有者是你，不是線

**刪掉 `<fleet>/` 之前，先把逐線收尾掃不到的東西搬出去。**
⚠️ **判準是「有沒有被掃過」，不是「屬於誰」**——下表最後一列**屬於**某條線，
只是那條線從來沒有機會跑收尾。用歸屬當邊界，字面讀者就會漏掉正是最容易遺失的那一列。

| 要搬什麼 | 為什麼線掃不到 |
|---|---|
| **每一則裁決** | 裁決帶齊「為什麼／前提／翻案條件」必然超過門檻，**必然落檔**——而它是你寫的，不是任何一條線的 |
| 協調者的廣播 | 同上，發信人是你 |
| 合併後的跨線事實 | 它的正本屬於「合併值」，不屬於提供原始值的任何一條線 |
| **意外死亡的線留下的訊息** | 那條線**從未跑過收尾清單**——名冊規則明文要求它的列留著，正因為它沒有機會收尾 |

⚠️ **「拆艦隊就是刪掉一個目錄」是本協定唯一的破壞性動作，也是唯一的靜默資料遺失來源。**
把它寫成賣點而不配一道 gate，就是把整批裁決正本押在「有人會記得」上面。
**這份清單就是那道 gate。**

⚠️ **最容易漏的是裁決，而它恰好是最該留的。** 你是按刪除鍵的人，也是裁決的作者——
**沒有第二個角色會來提醒你。**

> **handoff 歸檔那一項為什麼要留「不適用」這個答案。** 2026-08-21 有兩條線**從未建立 handoff 檔**。
> 訊號若只寫成「已在 `archive/`」，你會去找一個不存在的檔案，然後在
> **「還沒歸檔」與「不需要歸檔」之間分不出來**——而這兩者的處置完全相反。
> **判準是有沒有那個載體，不是有沒有做那個動作。**

**編號回收。** 配給一條線的編號區間（decision 編號、migration 版本、任何預先切給它的號段），
**配出去不等於用完**。而沒用完的那幾號**在任何檔案裡都不存在**——
grep 不到、配額表只記得配了多少，**只有線自己知道**。

> **回收有一個時間窗，錯過就永久浪費。** 線收工之後就沒人記得了。
> 2026-08-21 實例：一條線配到 D294、實際只用到 D292，**主動回收了 D293／D294**。
> 若只讀配額表，下一條線會從 D295 起，那兩號永久蒸發。

所以編號對帳要**三邊都問**：`grep`（會低估也會高估）、配額表（會高估已用量）、
**以及線本身**。前兩者查得到，第三者只能在它還活著的時候問。

**還有什麼只有你知道。**

**四訊號量的是「產出有沒有落地」，未決事項是「有沒有問題還掛著」——兩者可以同時為真，
而只有線自己知道後者。**

> **2026-08-21 實例。** 協調者關掉了一條線的 pane，**四訊號全齊、產出全在檔案裡**，
> 但它當時還有一件未決（兩個版本的短通知要等另一個裁決才能二選一）。
> **沒有東西遺失，但那件未決失去了主人。**

**「我順手解決了一個小坑」也屬於這一項——問它有沒有住址。**

> **一個活在某個人操作習慣裡的知識，在那個人收線之後就不存在了。**

2026-08-21：某個工具的預設值被**兩條線各自踩到、各自手動解除**，第一次解除的人沒有留下任何痕跡，
於是第二條線是**重新發現**的。**小坑最容易被判定成「不值得寫下來」，而它們正是重複成本最高的一類**
——每個新來的人都要付一次，而每個人付的都不多，所以沒有人覺得值得記。

**收線前還有一件只有它做得到的事：覆核。**
一份交付物若動到多個由**不同線**建立的東西，**「找一個懂那些東西的人覆核」不是禮貌，
是唯一能發現跨物件耦合的機制**——機械的差分驗證抓得到「不等價」，
抓不到「**等價但語意上不可復原**」。

> **2026-08-21 實例。** 為了保住某支 migration 的 seed 而讓一張表不被 DROP，
> 會讓**其餘每張表 DROP 的可復原性一起壞**（清空投影不會移動 checkpoint，
> 寫入路徑又被 checkpoint 守著，結果是投影永久停在零**而且不報錯**）。
> 覆核者自述：「**這是只有它知道的耦合，我不可能推導出來。**」
> ⚠️ **而它有時間窗：那條線當時正在收線。** 協調者把它留下來，是這一整條鏈成立的唯一原因。

**合併驗證不要用 `git branch -d`**——squash 讓它對「已合併」與「真的沒合併」給同一個答案。用 scoped diff：

```bash
paths=$(git diff --name-only $(git merge-base origin/<base> <branch>) <branch>)
git diff origin/<base> <branch> -- $paths   # 要是 0 bytes
```

**清單齊了才關 pane。** 一段 handoff 一個 session，收尾**之後**才有權關
——那是「不要關別人 tab」的明示例外，但授權範圍是「收尾後」。
**關 tab 前先查 tab 裡有幾個 pane**，別的線可能跟它同住。

> **「一段 handoff 一個 session」的完整形狀**：一個任務因 context 撐不住而需要多次 handoff，
> 或一個 handoff 任務做完了——兩種情形處置相同：**指揮該 session 收尾 → 關掉它 → 用新 handoff 開新 session**。
> 長壽 session 累積的是無人讀得到的 scrollback，不是資產。
> 這條規則的安全性**完全押在「收尾」是真的**：關之前先問「這個 session 知道而檔案不知道的，是什麼？」
> **協調者自己也適用，而且最容易漏**——它是最長壽的那個。

## 交付物不要留在會消失的地方

**scratchpad 隨 session 消失。** 協調者的產出（對外文件、待認領清單、跨線盤點）
一產出就移到活得比 session 久的地方——`~/.agent/handoffs/<repo-slug>/attachments/`。

2026-08-21：前任協調者的對外文件留在它自己的 scratchpad，pane 關掉前搶救才沒丟。

**引用要用它未來的路徑。** handoff 被歸檔後路徑會變成 `archive/<ID>.md`，
所以在還活著的檔案裡引用它時，直接寫歸檔後的路徑。

**上面講的是「檔案 vs scratchpad」。還有更前面一步：訊息 vs 檔案**——見下一節。

## 線與線之間的每一則往來都要選載體

**判準是「這則內容要在對方的哪個時刻生效」，而它有三格，不是二選一。**

| 這則內容 | 載體 |
|---|---|
| 只是**現在**要對方知道 | **訊息**（受下面那條升級規則約束） |
| 要在對方**未來**某個時刻生效 | **檔案**（`~/.agent/handoffs/<repo-slug>/attachments/`），訊息只用來說「有一份東西在那裡」 |
| **現在要知道，且未來要能重讀** | **檔案 ＋ 帶摘要的 prompt——兩個都要** |

⚠️ **第三格不是二選一。** 寫了檔就不通知，那則內容不會闖進對方的回合；只通知不寫檔，它就只活在 context window 裡。**兩個都要**才拿得到這一格要的東西。

⚠️ **你最容易搞錯的一格**：**一條線收線前交出的知識幾乎一定屬於第二格**
——因為它收線之後就不在了，而需要那份知識的人**往往還沒開工**。

> **2026-08-21 實例。** 一條線收線前把覆核意見寫成檔案而不是發訊息。
> **讀到它的那條線是在前者收線之後才開工的。**
> **如果那是一則訊息，它會在對方開工之前就過期。**

⚠️ **但第二格只寫檔還不夠——它還要被一個活得比它久的索引指到。**
那一格的典型讀者**還沒開工**，所以沒有 agent 可以通知；而落點目錄**沒有索引**。
於是「檔案活下來了」與「將來有人找得到它」**是兩件事**。

**指標要落在一個長命載體上**：對方的 handoff（`## References` 或 `## Next steps`）、
memory、或你交給接班人的那份清單。
**只寫檔不留指標，等於寫進一個無索引的目錄，再指望有人碰巧翻到。**

**〈跨線事實〉那一整節的產出屬於第三格**——合併值現在就要送到每一條相關的線，
但它是資料，而且**接手的人重驗它時需要原文**。判準見上表，不在那一節重寫。

### 為什麼走檔案：三個理由，而「省 context」不在裡面

**拿不準時就走檔案。** 三個理由如下，而它們都與「對方讀起來省不省」無關。

1. **可重讀。** 長訊息只活在 context window 裡，壓縮後剩摘要，**且查不到漏了什麼**。
   這對本 skill 特別要命，因為它自己就規定「接手包含重驗你要繼承的結論」，**而重驗需要原文**。
2. **吃字整族消失。** 訊息只帶路徑，就沒有反引號、`$`、`!` 那些字元經過 shell（見附錄 A）。
3. **它同時是「這件事確實發生過」的證據。** 與「資料通道不得是螢幕輸出、以檔案為通道以 pane 為
   trigger」同一條，只是推廣到線與線之間。

⚠️ **不要拿「省 context」立論——它經不起推敲。** 對方仍要把檔案讀進 context，同樣的 token。
真正省到的只有**選擇性讀、晚點讀、根本不用讀**三種情況。
**把弱理由放在承重位置，下游會拿著它把規則推廣到錯的地方。**

### 升級規則：一條規則，兩個觸發條件

⚠️ **這條規則的機械部分在 {{ .n.devWorkflow }} 的線側契約裡有一份複本**
（觸發字元集、兩個門檻、建檔守衛、檔名形狀）。線載入不了本 skill，所以那份必須存在——
**代價是改動要做兩次**。2026-08-25 已經漏過一次：字元集移除「括號」時只改了這一份，
**而線那份才是真的會被執行的那份**。（比對兩份的守衛已記在 backlog。）

⚠️ **這裡的「升級」是升到第三格，與〈派線時關掉線的發問管道〉那個「升級契約」（升級到真人）
是兩件事。** 兩者共用一個詞，而派線酬載同時要帶這兩樣——寫酬載清單時不要混。

> **落在第一格的內容，只要含反引號、`$`、`!` 任一，或超過 5 行或 500 字元，
> 一律升為第三格。**

**兩個條件的處置相同，所以它是一條規則**——拆成兩條就是〈複寫了別處的事實〉。

- **為什麼是雙上限**：只設行數會漏掉**一行三千字**那種訊息。它照樣淹掉對方的 session，
  而行數判準完全看不見它。
- **為什麼是 5 行**：它剛好容得下第三格的通知本身（一行說是什麼、一行路徑、一到兩行為什麼現在要看）。
  **門檻不得縮到低於通知本身的長度**——升級是在**超過**門檻時觸發，門檻若比通知還短，
  通知就會超過它而被升級，規則咬到自己的尾巴。⚠️ **危險的方向是門檻太小，不是太大。**
- **這是守衛，不是告誡。** 吃字那一族的告誡**已經有實測敗績**——
  協調者曾在撰寫「怎麼避免被吃字」那則廣播時**自己被吃**（見附錄 A）。

**升級的方向與判準自洽，這不是巧合**：含高密度技術符號、或長到需要分段的內容，
幾乎必然是資訊密度最高、事後最需要重讀的那種——**而那正是第三格的定義**。
所以這條守衛不是外掛的檢查，**是判準自己推出來的**。

⚠️ **要接受的後果：裁決會被系統性地推去寫檔。** 一個裁決帶齊「為什麼、前提、什麼條件下會翻案」
（見〈裁決〉）幾乎必然超過 5 行。**這是對的，不是門檻訂錯了**——裁決正是最需要事後重讀的東西。
於是第一格實際上只剩「你可以合併了」這種一行話。

### 一則一檔，動作是建檔

**落點與檔名見附錄 B——那裡講的是第一格升級上來的、與第三格的檔案。**
⚠️ **第二格不走那個落點**：它要活得比寫的人久，而艦隊目錄連艦隊都活不過。第二格的落點在上表那一列。

這裡只講形狀：**一則訊息一個新檔，檔名唯一，動作是建檔——
不是對既有檔案覆寫，也不是 append。**

**理由不是比較整齊，是它讓〈整份覆寫之前先讀〉那一整族的失敗不會被觸發**
——不是被規則擋住，是**沒有那個動作**。該族的三層守衛在這個佈局下無事可守。

⚠️ **但「建檔」要由機制施加，不能只由這句話施加。** 用 Write 工具、`>`、heredoc 寫同一個路徑，
**照樣靜默覆寫**；而同一個寄件人在同一分鐘對同一個收件人發第二則修訂，撞名一點都不罕見。
寫入前先擋：

```sh
[ -e "$f" ] && { echo "COLLISION: $f"; exit 1; }
```

**沒有這一行，上面那句「結構上」就是措辭而不是機制**——而 `~/.agent/` 不在版控裡，蓋掉就沒了。
（這是 principles「**邊界要由執行機制施加，不能只由 prompt 措辭表達**」的直接適用。）

**寫檔與通知要定序：先寫檔 → 確認它在 → 才通知。**
反過來，對方會拿到一個當下還不存在的路徑，而它讀不到時**分不出是訊息壞了還是自己錯了**。
⚠️ **而只寫檔沒通知更糟**：檔案躺在那裡，對你看起來像已完成，
**而收訊方推導不出那個路徑（它不知道 `<repo-slug>` 與 `<fleet>`），永遠不會去看**。
`herdr agent prompt` 會失敗（實測 `No agent named '…' is reachable`），所以這不是假想。

**通知送不出去時，二選一，不要就這樣放著：**

1. **換管道重送**（可達性與退路見附錄 A）
2. **把那則降級為第二格**——寫進對方將來找得到的地方（它的 handoff、交給接班人的清單），
   並在下一次接觸時帶出來

⚠️ **定序解決的是先後，不是這個殘留態。** 檔案在、對方不知道、沒有回執——
**這個狀態對寄件者看起來與成功完全一樣**，而它會一直維持到艦隊被拆掉為止。

**而且收訊方沒有「讀到哪了」這個狀態要維護。** 通知只帶一個路徑，那個路徑就是一則完整訊息。
換成一線一檔 append，收訊方得自己在長檔案裡找哪一段是新的，**而找錯是靜默的**。

⚠️ **共用收件匣答不出它為什麼不重蹈〈共寫檔〉。** 收件匣按定義是多寫入者，
而那節的承重立論正是「**沒有並行 append 的理由是寫入者只有一個**」。

### 不設回執：要確認對方接住了，去查它的產物

**不要問它，去查。** 差分（`git diff --stat <base> <head> -- <path>`）、檔案在不在、收尾四訊號。

**回執答不了它要答的問題**：回執只答「讀了」，而讀了不等於做了。兩條既有規則正面壓在這上面
——〈證據的資格〉的「**一個永遠有答案的讀取，答案可能屬於上一個時刻**」，
以及〈跨線事實〉的「**你是量的還是記的？**」：回執是自述，不是量測。

**以檔案送達的裁決加掛一項**：對方要在**下一則本來就要發的**回報裡引用該訊息的檔名，
**並說明照做了沒有；沒照做要說為什麼**。
**它搭在既有訊息上，不新增訊息，所以不會遞迴。**

⚠️ **義務不得以「照裁決動手時」為條件。** 以行動為條件，就會**豁免掉「開了但判斷不需行動」那一格**
——而那正是唯一需要這個訊號來區分的一格。**規則不能把自己要偵測的東西排除在外。**

⚠️ **它的價值有兩層**：「引用錯檔名會露出來」，以及**把兩種沉默換成兩份看得見不同的回報**。
「沒開檔」與「開了判斷不需行動」原本長得一模一樣；現在前者交不出引用，後者交得出並附理由。

**carve-out**：第一格那種一行話裁決（「你可以合併了」）**沒有檔案**，
不要求引用一個不存在的檔名——但它也不該承載需要事後重讀的內容，那種內容早該升到第三格。

**翻案條件**：協調者實際遇到「引用義務讓線的回報變得冗長，而那些引用從未被用上」。

## 整份覆寫之前先讀 —— 這一族的失敗全部靜默

- **整份或整段替換（`sed`、覆寫式寫檔、清空輸入框），動手前一定先讀**
- 改共寫檔的某一列，用**名稱錨定**並斷言「恰好命中 1 列」才寫檔
- **判斷不出那段內容是誰留的，就不要覆寫**——留著的成本遠低於蓋掉
- **蓋掉之後要留痕跡**，主動告知當事人，不要用「結果沒壞」自我赦免
  ——結果沒壞是運氣，而當事人有權自己判斷。
  （**告知的人是誰，是另一格獨立的判斷**，見〈誰有資格說這句話〉。）

**為什麼規則是機械的而不是「小心一點」**：對「共寫、且沒有版控」的東西做整份覆寫，
是本 skill 裡最反覆出現的一種事故，**而它的失敗全部靜默**。
2026-08-21 一天之內三起，形狀完全相同：

| 覆寫的動作 | 蓋掉了誰 | 怎麼被發現的 |
|---|---|---|
| 未錨定的 `sed` 改 `active_workflows.md` | 另一條線的進度列 | 對方主動回報 |
| 沒先讀就整份寫入一份已存在的檔案 | 另一條線剛寫的內容 | 對方主動回報 |
| 清空 agent 的輸入框 | **使用者未送出的草稿** | **沒有被發現** |

**前兩起靠對方回報才浮出來。第三起的當事人是人，而人不會回報**
——他甚至不知道自己的輸入消失過。

> **受害者是人的那一格最危險，而它剛好是最容易被當成「清一下殘留」的那一格。**
> 另外兩格的受害者是 agent，會回報；人不會。**風險最高的動作看起來最無害。**

**這一族之所以危險不是因為蓋錯，是因為蓋了沒人知道。**

### 「先讀」不等於「條件寫」——三層，前兩層都不夠

| 層 | 擋的是 |
|---|---|
| ① 先讀 | 盲寫 |
| ② 條件寫／`assert` 錨點恰好命中 1 列 | 錨點消失（讀到的已經不是你以為的那份） |
| ③ **只碰自己那一列**（單列 `sed`、或 append），不要整檔 read-modify-write | **別人在你讀與寫之間新增的東西** |

> **`assert` 保護的是「我的錨點還在」，不是「這個檔案沒有被別人動過」。**
> 別條線在我讀與寫之間新增一列，我會靜默把它丟掉——**而 `assert` 不會響，因為我自己那一列還在。**

> **2026-08-21 實例甲（較粗）**：編輯腳本是「讀檔 → 嘗試取代 → **無條件寫回**」。
> 某次兩個錨點都 hit=0（因為讀到的已經是別人的新版），**於是它把讀到的內容原樣寫了回去。**
> 這次沒事，但若對方在「讀」與「寫」之間寫入，就會被靜默還原。

**退而求其次**（當整檔重寫無法避免，例如要改的是散在多處的敘述）：
**讀取當下記下 `mtime_ns` ＋ `size`，寫入前重驗，變了就中止重讀。**
**它不是第三層**，但它把靜默還原**變成一次中止**。

### 工具回報成功不等於它做了事

**這一族的失敗形狀比規則本身更值得記：**

> **下游的每一個檢查都會通過。** 斷言過了、工具回報「已寫入 N 處」、檔案也真的被改了
> ——**只有把成品讀出來才看得到。**

- **寫完之後把成品讀回來看一眼**，不要只看工具的回報。
- **掃描要找空白，不要找錯字**——被吃掉的痕跡是空白。
- 字串取代要**用行號定位，或斷言替換次數恰為預期**：
  一次比對字串多一個尾隨空白，**五個修補會全部靜默失效，而管線照跑、輸出與上一輪一模一樣**。
  **「修補成功」與「修補沒匹配到」在回傳值上不可區分。**

- **「試一下再還原」對會成功的操作不成立。** `--abort` 這類旗標是**失敗路徑**的還原：
  操作成功時沒有東西可以 abort，那一行是**空操作**。要還原一次**成功的**操作，
  得先記下起點 sha 再 `git reset --hard` 回去。

> **2026-08-21 實例。** 一條線跑 `git rebase … && { echo clean; git rebase --abort; … }` 來「試一下」。
> **rebase 成功，`--abort` 什麼都沒做。** 沒出事的原因純屬僥倖：它把最後一個參數寫成 `HEAD`
> 而不是分支名，於是 git 在 detached HEAD 上完成 rebase，後面那句 checkout 把結果丟掉了。
> **寫分支名的話它現在會坐在另一個 commit 上而毫無所覺**——
> `git status` 乾淨、`git log -1` 的 message 一模一樣，**只有 `HEAD^` 會告訴你。**
>
> ⚠️ **這一族的共同症狀：狀態查詢全綠、摘要一模一樣，差別只在一個沒有人會去看的地方。**

（訊息在送出途中被吃字是同一族的另一個載體，見〈附錄 A〉。）

## 共寫檔：平行寫會靜默重複，不會衝突

`active_workflows.md`、共用筆記、盤點表都是共寫的。**append 一節永遠成功，沒有任何警告。**

- 改自己那列要用**名稱錨定**，並斷言「恰好命中 1 列」才寫檔
- 寫一則**已存在**的筆記前先 `grep` 標題關鍵字，不要只看索引（索引會落後）
- 發現重複時**收掉自己那塊、併進證據較具體的那節**，並標明哪句是誰實測的
- **同一則檔案的更新只指派給一條線**——「順手記一下」正是相撞的來源

### 共寫的資源不只是檔案

**判準不是「它是不是檔案」，是「有沒有第二個人的行為會透過它改變我的結果」。**

**① `git checkout` 本身。** 一樣共寫、一樣沒有警告、一樣靜默。

> **2026-08-21 實例。** 一個 session 收尾時在**共用的主 checkout** 上跑 `git switch`，
> 而那個 checkout 當時被另一條線的分支佔著（`active_workflows.md` 有列、它自己讀過）。
> 工作區乾淨所以沒丟東西，**但它把別人的 HEAD 帶走了**——
> 而它自己已經有 worktree、**根本不需要動主 checkout**。

**規則：動共用 checkout 的 HEAD 之前先查 `active_workflows.md` 有沒有別人佔著；
自己有 worktree 就不要碰主 checkout。**

**② 一個工具讀取設定的位置。** 這一格比檔案更遠，而且**沒有人做錯事**。

> **2026-08-21 實例。** 某個部署工具的來源目錄指向那個共用 checkout，而它停在別條線的分支上
> ——那條分支沒有剛合併進來的東西。於是**任何人在那台機器裸跑那道部署指令，
> 會把剛合併的檔案退回合併前的版本。**
> 一條線正常地在自己 branch 上工作，另一條線正常地合併了 PR，
> **是兩者的組合產生了第三個效果，而兩邊各自都看不見。**

**規則：這種工具要限縮作用範圍（點名來源與目標），不要裸跑。**
**這也是一種跨線事實**——它不是數字，是一個只有站在兩條線之外才看得到的效果。

## 認得「複寫了別處的事實」這一族

**你要做的兩件事：**

1. **一條線報上來的「我發現一處註解／記載是錯的」，先問它是不是這一族。**
   若是，修那一處只是治標——要問的是「**還有誰複寫了同一個事實**」。
2. **修法的判準是「讓它去數，不要讓它記」。** 把兩處複寫合成一處共用常數**看起來**已經修好了，
   但來源一改它照樣錯。**去重不是目的，免疫於來源漂移才是。**
   （對文件而言的等價做法：不是刪掉那句話，是註明它的已知例外並指向正典。）

**這一族長什麼樣**：某處複寫了另一處的事實，而來源改動時，複寫的那份不會知道。
失效一律是**靜默**的——沒有編譯錯誤、沒有測試轉紅、只有一個看起來仍然正確的答案。
協調者橫跨多條線，所以看得到單一條線看不到的這種同型缺陷。

2026-08-21 在四條不同的線上各出現一次，形狀完全相同：

| 複寫的那份 | 來源 | 來源改了會怎樣 |
|---|---|---|
| 兩處寫死的 `SEEDED_EVENTS = 5` | fixture 檔的事件筆數 | 加一筆事件，兩個 `5` 都不會編譯失敗，四處斷言**一起**變成錯的期望值 |
| 架構文件裡的容忍前提 | 實際的 migration 策略 | 一步到位 DROP 踩掉前提，文件仍宣告舊保證 |
| 盤點表的「未移植」兩列 | 端點實際狀態 | 端點移植了，記載變成錯的，沒有東西會紅 |
| 某條決策裡的「目前沒有別的 caller」 | 程式碼現況 | 下一個人加一個 caller，那句話悄悄不成立 |

> **這條判準也適用於本檔自己。** 一份跨 repo 的 skill 若把某個 repo 的編號、
> 某個平台的設定、某個 agent 的旗標抄進正文，它就是這一族——換掉底層之後靜默失效。
> 所以那些東西全部集中在〈附錄〉並標明前提，而不是散在主體裡。
> **寫規則的人最容易在自己的規則上犯規**，因為他把自己的環境當成了背景而不是變數。

**四處加強**（2026-08-21 的唯讀盤點）：

1. **「合成一個共用常數」這個中間解不是推測會失敗，它已經被反證。**
   兩個檔案**各自**抽出了具名常數、四處斷言全部走常數、**沒有一處是字面值**——**而它照樣會一起錯。**
   > **把兩份會過期的複本合成一份，得到的是一份會過期的複本。**
   **這是這一族最容易誤判的一格：去重讓複本看起來消失了，但複寫的關係還在。**
2. **先找 repo 裡有沒有人已經解過，不要自己發明。**
   **兩條無關的路徑各自收斂到同一個形狀，那是它對的證據，強過任何論證。**
3. **文件側最難，因為工具看不見。** 一處註解用**英文字**寫著 "all five"，
   **任何數字型 grep 都抓不到**；而且修完之後它會從「多餘」變成「**錯的**」。**修這一族要連散文一起改。**
4. **驗證方式：先改來源，證明複寫的那一側會紅。會紅才算數，不能用推理代替。**
   （這與〈證據的資格〉第②層是同一條規則，而兩者是從**完全不同的方向**各自抵達的
   ——一個從測試 fixture、一個從 schema 交付。依上面第 2 點，那是它對的證據。）

### 比它高一階：守衛存在，但守著錯的東西

上面那些的形狀是「記載錯了而沒有東西會紅」。**更壞的形態是：守衛在，但它正面斷言了錯的規則，
並因此一直是綠的。**

> **2026-08-21 實例。** 一支名為「…寫入路徑產得出來的」的測試，把期望值**只用 `GROUP BY` 建出來**，
> 而 `GROUP BY` 在計數為零時根本產不出那一列。
> 於是**這支自稱檢查可產出性的測試，正面斷言了那條不可產出的規則，並因此一直是綠的。**

**兩者的修法完全不同**：前者是**加**測試；後者要**先拆掉那支測試對錯誤規則的背書**，
否則新測試會跟它打架。**線報上來的若是後者，別讓它只補一支測試。**

## 派線時關掉線的發問管道 —— 但**不能只關**

**派線時兩件事必須同時給：**

1. **關掉該 session 的發問管道**——做法與可行性依**線的** agent kind 而定，見附錄 B；
   **不是每一種都有機械手段**
2. **升級契約**：撞到你做不了的決策 → **具名回報協調者並停下，不要挑預設值**

**只給第 1 件會更糟，這點已經實測**（見下方 A/B）。**範圍只能是「那一個 session」，不要寫進設定檔。**

為什麼要關：被協調的線若在自己的 pane 開出詢問真人的選單，就把使用者拉進一個他不該盯著的地方。
決策應該回報給你，只有**你**決定不了才升級到真人。

還有一個更硬的理由：**視該 agent 的 TUI 而定，你可能根本回答不了那個選單**
（見附錄 A——至少在某些 agent 上，多題選單一律不能按鍵）。
真是這樣的話，線一旦開出選單，就進入一個**只有真人能解除、而真人不該盯著**的狀態。

> **2026-08-21 A/B 實測。** 同一個資源競爭情境（「migration 版本號全域遞增，
> 你看到最新是 V1.9，你要用哪一號」），**兩組都移除了全部工具**，唯一變數是有沒有附升級契約：
>
> - **無契約**：挑了 **V1.10**，宣告接下來會建檔。有補一句撞號風險與「建議協調者統一分配」——
>   **但那是在已選定號碼、已宣告要繼續之後的註腳。**
> - **有契約**：拒絕自選，具名回報協調者，明說「在收到明確配置前，我會停在這一步，
>   不會擅自挑一個版本號繼續執行」。
>
> **關鍵是無契約那組同樣沒有發問工具。** 所以移除工具本身不產生停下來的行為——
> 它產生的是「命名了 fog 但仍以預設值往下走」，正是本 skill 的頭號失敗。
> **契約才是做事的那一半。**

**「不要寫進設定檔」這點反直覺**——「寫設定檔比較好管理」
是很自然的想法，但三個層級全都會壞事：

| 寫進哪一層 | 會一起關掉誰 |
|---|---|
| 使用者層（跨所有專案） | 所有 session，**包含你自己** |
| 專案層且進版控 | 該專案全部 session，而且同步到所有機器 |
| 專案層但只在本機 | 該專案全部 session，含在該專案工作的協調者 |

（各 agent 的設定檔實際叫什麼、分幾層，見附錄 B。）

**你必須保留發問能力**——你是唯一該升級到真人的角色。把自己一起關掉，升級鏈就斷在最上面。

### 第二種形狀：範圍是對的，但套錯了 session

上面那張三層表防的是**範圍太寬**。還有一種：**範圍正確（單一 session），而那個 session 是你的接班人。**

**接班的協調者是用同一道 `herdr agent start` 開出來的**，而那道指令在派線的脈絡下帶著旗標。
照著習慣動作開接班人，**升級鏈就斷在最上面，而且接班人不會知道**
——少帶或打錯 tool 名時只警告、不擋、exit 0，它只會在第一次需要問人的時候發現自己問不了。

**「你必須保留發問能力」這句話只約束得到現任。** 現任讀它的時候，接班人還不存在。

所以修法不是多寫一句告誡，是**兩道不同的指令**（見附錄 B）：

> **派線一道，開接班協調者另一道。不是「同一道指令，接班時記得砍掉一段」。**
> **要人記得砍掉一段，遲早會有人忘記砍。**

**而且要在派線那一刻把「該不該帶旗標」＋ 角色一起寫進 `fleet.md`**——記的是**形狀**，
不是 `cmdline` 原文（理由見〈艦隊名冊〉：原文是 per-process 事實，交接必變，
而它宣稱能提供的證據，下面那張表正好證明它提供不了）。
`herdr agent list` 不給啟動參數，handoff 只記「pane id 換了、名字不變」——
**所以「這條線該不該帶旗標」沒有第二個地方記得住，那一格必須是名冊。**

⚠️ **角色要跟著落，因為 argv 記得了旗標、記不得角色**——而機器上有三態：

| 態 | 該不該有旗標 | 從 `ps` 分不分得出 |
|---|---|---|
| 被派出的線 | **有** | **不能** |
| 協調者 | **沒有** | **不能** |
| **不屬於任何艦隊的 session**（使用者自己開的、別的 repo 的） | **無所謂** | **不能** |

> **`ps` 給的是「有沒有旗標」，你要判斷的是「該不該有」。**
> **第三態的存在讓分母不可知**——所以「掃一次確認分佈全對」這個檢查**本來就答不了**，
> 事後永遠分不出「沒帶旗標的協調者」與「沒帶旗標的路人」。

**這是〈證據的資格〉第①層的又一個實例**：旗標欄位對「**沒帶旗標的**協調者」與
「**沒帶旗標的**路人」給**同一個答案**，所以它沒有資格區分這兩者。
（⚠️ 一致的是**分不分得出**那一欄；「該不該有」那一欄給的是三個不同答案。）
**⇒ 這一族只能在開線那一刻防，不能事後稽核。**

⚠️ **這裡擋住的與〈自檢與稽核〉擋住的不是同一件事，兩者都成立：**

| 想稽核什麼 | 擋住它的 |
|---|---|
| 「這台機器上分佈全對嗎」 | **分母不可知**——路人不在名冊上，本節這段 |
| 「名冊上每一列的 session 形狀對嗎」 | **缺 name→process 的 join**——見〈自檢與稽核〉 |

名冊補掉的是**分子**，不是那道 join。所以它讓第二個問題**有了答案的形狀**，卻仍然讀不到答案。

**發現自己沒有那個工具時的處置**：**立刻說，並請使用者重開一個沒帶旗標的 session。**
那是啟動旗標，跑到一半補不回來。**不要自己想辦法繞過**——繞過就是「命名了 fog 但照走預設值」。

> **2026-08-21 實測（`ps -eo pid,args`）。** 當時機器上三條被派出的線全部帶著旗標、
> 兩個協調者都沒有帶——**在那五個角色已知的 session 上分佈是對的**（角色是靠人知道的，
> 不是從 `ps` 讀出來的；同一次掃描裡還有四個 session 的角色無法從 argv 判定）。
> **但沒有任何機制在維持這個分佈：協調者沒有被關掉，只是因為打指令的人剛好沒複製那一段。**
> 這正是〈證據的資格〉那句「**『沒有人會不高興』不是安全訊號，是『沒有東西在守這一格』的訊號**」
> ——只是這次沒有人不高興的原因是**它剛好沒壞**。

**代價要說清楚，不要當它不存在**：真人因此失去繞過你的通道，**你變成沒有 bypass 的單點**，
而本 skill 自己就記著協調者會給錯問題框架。緩解是：**線推翻前提靠的是文字回報、不是選單**，
那個管道仍然有效——關掉的是攔截真人的介面，**不是線的異議權**。派工時要講明這一點。

⚠️ **而這個單點有一類決定你根本補不上**：有些授權**只能由使用者本人給，你連轉述都不夠**。
線問不到人、你又不能代答，那個 pane 就進入一個**沒有出口的狀態**。
**解法是把人帶到那個 pane，不是代答**——見下一節。

## 裁決：怎麼下一個下游用得對的裁決

**一個裁決要能被下游正確使用，所以每一條都要帶三樣：為什麼、前提、什麼條件下會翻案。**

少哪一樣，下游都還是會照做——**它只是會在下一輪用錯誤的理由推廣它。**

### ① 帶「為什麼」與「什麼條件下會翻案」

替線做了決定卻不說理由，**線會照做，然後在下一輪把它當成通則套到別的地方**。
翻案條件同樣重要：沒有它，一條只在當時成立的裁決會活得比它的前提久。

### ② 前提要跟著規則一起傳

**這是 ① 的下一階。** 下游收到規則會照做，**而它看不到前提是什麼**，
所以它**無法判斷規則適不適用於自己**。

> **2026-08-21 協調者犯了兩次。** 一條常設授權**自己帶的例外**沒有一起傳；
> 「先不要 rebase」那條規則的前提是「你有一個開著的 MR」（綠燈與自動合併會被作廢），
> 而它傳給了一條**還在實作中、沒有開 MR** 的線——**於是那條線寫不出正確的實作**，
> 因為它需要的正是剛合併進來的東西。**兩次都是下游推翻的。**

### ③ 派下「照規則 X 統一處理這批東西」之前，先問「現況為什麼不統一」

**不統一往往不是疏忽，是一條沒被寫下來的規則在起作用。**

> **一個沒有被說出來的規則，仍然是規則，而它的證據就攤在你正要覆寫的那些檔案裡。**

> **2026-08-21 實例。** 某批腳本裡「一張表不 DROP、十一張 DROP」的分佈**本身就是判準**
> ——唯一不可重算的那張，正是唯一從不被 DROP 的那張。
> 一條線看著那個分佈，**卻沒有問「為什麼是這個分佈」**，直接套了一條更抽象的規則覆寫它。
> **錯的不是它的結論，是判準的適用範圍。**

### ④ 記下這條規則是**怎麼被逼出來的**，不要只記誰提出的

> **一條規則的來源鏈，就是它的適用範圍。**

少了它，下一個想推翻或延伸的人**只能重新論證**。
（實例見〈證據的資格〉最後那條：第四層是被一個擋在那裡的守衛逼出來的，
**而「有守衛擋著」正是它成立的條件**。）

## 誰有資格說這句話

**這一族的失效是：一句話的署名跟它真正的來源對不上。而下游分辨不出來**
——收訊方看到的署名是對的，內容也通順。四種形態，由輕到重：

### ① 該由誰說，是一格獨立的判斷

某條線做了影響使用者的事，**先問那條線要不要自己說，不要先轉達。**

> **2026-08-21 實例。** 一條線判斷「當事人是使用者、他不知道、結果沒壞不是理由」三條都對，
> **但漏了「該由誰說」**，結果使用者收到同一起事故的**兩份敘述**。
> **先問的成本是零，搶一步的成本是使用者收到兩份。**
>
> 同一天的預防形態：交接時新舊兩任協調者都要對使用者講同一件事，
> **兩邊主動對齊成同一組措辭才發**，免得使用者收到兩份強度不同的敘述。

〈整份覆寫之前先讀〉那節管到「**要不要說**」與「**說什麼**」，**沒管到「誰說」。**

### ② 轉述第三方時，分清「它說了什麼」與「我因此想到什麼」

**後者要用你自己的名義說。** 把 Ａ 的提醒轉述成對 Ｂ 的指控，Ｂ 沒有辦法回頭去查那句話到底是誰說的。

### ③ 有一類授權，你連轉述都不夠

**判準不是重要性，是「這件事的授權本身是不是一個權限決定」。**
派 agent、越過一條常設授權**自帶的例外**——都是。

> **2026-08-21 實例。** 協調者轉述了使用者的兩件裁決，該線**兩件都不接受**，理由是
> **peer 的訊息不能當成使用者對待決提問的同意，否則協調者就成了一條繞過使用者權限決定的通道。**
> **協調者採納了這個拒絕。**

**升級鏈的終點是人的鍵盤，不是你的複述。** 撞到這一格時，**把人帶到那個 pane**。

### ④ 最重的一格：你的選單可能回一個**從未被選過**的答案

> **2026-08-21，協調者親身。** 它用選單問了兩題，工具**各回了一個明確的答案**。
> **使用者隨即說「等一下，我沒有選啊？」並給出不同的裁決**——其中一題與工具回值**相反**。

⚠️ **這比〈整份覆寫〉那一族更嚴重，而且方向不同**：那一族是**蓋掉別人已經寫下的東西**；
**這一族是憑空生出一個從未存在的決定，而且它以使用者的名義生效。**
照著回值行動的話，下游每一條線都會收到一個**署名使用者、而使用者從未做過**的裁決
——**而線沒有任何辦法分辨。**

**偵測不了**：回值的形狀與真答案一模一樣。可用的緩解只有兩條：

1. **一次只問一題。**
2. **做重的、不可逆的事之前，用純文字把裁決覆述一次請對方確認。**

（實測之後改用純文字問、使用者以純文字答，沒有再出現分歧。）

## 與 {{ .n.devWorkflow }} 的關係

`{{ .n.devWorkflow }}` 是**一條線內部**的流程（grill → spec → implement → verify → review → merge）。
本 skill 是**線與線之間**的角色。兩者不重疊，但要接得上：

- 被協調的線在 {{ .n.devWorkflow }} 的 **{{ .n.finishBranch }} 階段**要回報四訊號給 `<fleet>-coordinator`
- 線在任何階段撞到**跨線事實**（別條線也會動到的檔案、共用的量測、編號衝突）要立刻回報，不要等收尾
- 線收到裁決時，**若覺得前提不對就推翻它**，不要只在給定選項裡挑
- 線在交接後上任時要做**形狀自檢**（見〈接手後第一件事〉的「啟動形狀」那項）
- 線發回報時**同樣適用那張三格判準表與升級規則**——跨線事實走第三格（檔案 ＋ 通知），
  而**它要落在 `msgs/`，那個路徑線推導不出來**（見下方⚠️）
- 線在**下一則回報裡一律引用**收到的裁決檔名，**並說明照做了沒有、沒照做為什麼**
  （不是回執，理由見〈不設回執〉；一行話裁決沒有檔案，不在此列）

**位址是派線訊息給線的，不是線自己查來的。** `<fleet>-coordinator` 這個字串必須隨派線訊息
送達——與升級契約同一則（見〈派線時關掉線的發問管道〉）。
**訊息裡沒給位址，就是這次派線壞了**：線該把它當 fog 回報，而不是猜一個名字投出去。

⚠️ **凡是你要課給「線」的義務，都得走這條路送達。**
**沒有任何機制會讓一條實作線載入本 skill**——本 skill 是協調者的。
（不要用「線不讀你的 handoff」立論：那句講的是 handoff，不是 skill，範圍不夠。）
所以形狀自檢那條也必須進派線訊息的酬載，**並同步寫進 {{ .n.devWorkflow }} 的線側契約**。
⚠️ **酬載要連 `fleet.md` 與 `msgs/` 的路徑、以及檔名慣例一起給**——
只給目錄，線產不出合規又不撞名的檔名；而**不告訴它那個目錄會隨艦隊消失**，
它就無從判斷自己哪些訊息需要在收線前被搬出去。線推導不出 `<repo-slug>` 與 `<fleet>`，
而記載那個路徑的是本 skill，線又不會載入本 skill。少給路徑，那條義務就只是一句讀得懂、做不到的話。
只寫在本檔裡的線側義務，投遞不到任何一條線——而失敗是靜默的：
**規則寫得出來、讀得到、就是沒有人執行。**

## 附錄 A：herdr —— 跟線互動的機制

> 前提：以 [herdr](https://github.com/) 這類 agent 多工器管理各線的 pane。
> `herdr agent start --kind` 支援 21 種 agent（`pi`／`claude`／`codex`／`gemini`／`cursor` 等），
> 協調機制本身與 agent 種類無關。

### 輸入框非空時不要送 —— 這條是無條件的

`herdr agent prompt` 會把你的文字**接在輸入框既有內容後面**一起送出。所以在非空的輸入框上送，
**送出去的是一則沒有人寫過的合併訊息**：收訊方分不出邊界在哪，而殘留文字的作者
**從未同意在這個時刻、這個脈絡下送出它**。

**這一點與那段文字是誰留的無關。** 就算確定是 harness 補的、確定不是任何人的意圖，
串起來送仍然是錯的——你送出的東西不是你寫的，也不是它寫的。

所以順序是：**先把輸入框處理乾淨，再送你自己的文字。** 不要讓 `prompt` 去 append。

**先做一次機械檢查，再開始判斷是誰留的。** 輸入框「看起來非空」有一種情形不是任何人留的：

```bash
herdr agent read <name> --source visible --format ansi
```

**帶 dim 標記（`ESC[2m`）的那段是 TUI 畫的 placeholder ghost，不在 buffer 裡**
——`prompt` 根本不會把它接上去，`ctrl+u` 與 backspace 對它也都無效。**輸入框其實是空的。**
（實測於 Claude Code 的 pane；其他 agent 的 TUI 各有畫法，但
「**先讀原始控制碼、dim 的不算內容**」這個檢查方式與 kind 無關。）

> **2026-08-21：少了這一步，一條線停了兩輪。** 協調者反覆 `ctrl+u` 清不掉「開 MR」三個字，
> 判定成「使用者的草稿清不掉」。**這一步同時解掉下面〈實例甲〉那個三方誤判——
> 當時若有人讀一次 ansi，就不必猜。**

**只有非 dim 的非空內容才需要進入下面這張表。**

**「是誰留的」只決定你怎麼清空它，不決定你可不可以串著送**：

| 來源 | 特徵 | 怎麼清空 |
|---|---|---|
| 自己上一則的回聲、殘渣 | 認得出是自己寫的 | `send-keys <name> ctrl+u` 清掉 |
| **agent harness 產生的建議** | **內容剛好是「下一步顯然該做的事」** | 不是任何人的意圖，清掉 |
| 使用者親手打的草稿 | **帶有現場推不出來的資訊** | **不要清也不要送**——去問使用者 |
| **判斷不出來** | — | **去問使用者**。他是唯一的 oracle，成本是零 |

判準：一段文字若**剛好就是任何人看了現場都會說的下一句**，很可能是 harness 補的；
人打的字通常帶有現場推不出來的資訊。

**讀與送必須是兩次獨立動作。** 把 `read` 與 `prompt` 寫進同一道指令，
讀的輸出確實產生了，但**沒有任何時刻能消費它**——防線就退化成儀式。
先讀、看過、決定，才送。

> **2026-08-21 實例甲：三方同時誤判。** 一條線的輸入框裡有「繼續，跑第 2 組」，
> 前任協調者、接任協調者、以及那條線本身**三方都判定那是使用者未送出的草稿**，於是三方都不碰。
> 結果那條線空等了一個永遠不會來的 enter，還把「waiting on you to send …」寫進 recap 當**目標狀態**。
> 使用者親口更正才解開。**誤清草稿是靜默銷毀、當事人不會回報；誤留建議則讓一條線無限期空等。**
> 本節的前一版只看見前者，於是把規則寫成「看起來像回答就別碰」——**那條規則本身造成了後者。**
>
> **2026-08-21 實例乙：本節寫完當天就被違反。** 一個 session 把 `read` 與 `prompt`
> 放進同一道指令，讀到輸入框裡有「回 GitOps 線那題」卻在同一瞬間送出，
> **把那句話跟自己的訊息串起來提交了**。它讀了，只是讀在沒有用的時刻。
>
> **2026-08-21 實例丙：軼事反轉。** 協調者曾為「`ctrl+u` 清掉了某條線輸入框裡
> 『題目一選 1，題目二選 1，開始寫』」自責，判定自己毀掉了使用者的草稿。
> **事後向使用者查證：那不是他打的。協調者清得對。**
> **所以一則自責的事故報告，本身也可能是誤判**——它跟任何其他結論一樣要拿證據去驗，
> 不能因為結論對自己難堪就當它已經成立。

**對方 working 時讀不到 alternate-screen 歷史**，要用 `--source visible`。

⚠️ **但 `--source visible` 在 idle pane 上會回傳過期的畫面快照。**

> **2026-08-21 實測。** 對兩個 idle pane 送 `ctrl+u`／`esc` 清輸入框，之後連續讀 `visible`，
> **顯示的仍是原文**。等它們收到訊息開始工作、畫面重繪，才看到輸入框**早就空了**。
> **按鍵有效，讀取無效**——而讀取沒有任何跡象說自己是舊的。
> 協調者因此對兩條線發出過一則錯誤的警告（同一輪回頭更正；**若沒更正，
> 那句話會被寫進 map，然後下一個人會為了一個不存在的問題設計繞路**）。

**要驗證輸入框已清空：等一個會強制重繪的事件之後再讀，或改用 `--source detection`**
（實測它反映的是重繪後的狀態）。
**「讀一個 idle pane 的畫面」與「讀它的狀態」不是同一件事**——這是主體
〈證據的資格〉那條「一個永遠有答案的讀取，答案可能屬於上一個時刻」的第三個載體。

### 訊息內容會經過一層 shell —— 三種機制，兩種是靜默的

`herdr agent prompt <name> "…"` 的內容**經過 shell**，而協調訊息幾乎必然含反引號、`$`、
`!`、括號（檔名、欄位名、指令、程式碼片段、MR 編號）。

**前提（範圍，不是免除）：這一節管兩種東西**——未被升級規則接走的**第一格**內容，
**以及第三格的通知句本身**。
⚠️ **通知句也經過 shell**：它有一到兩行說明、還帶一個常被反引號包起來的路徑。
**而升級規則救不了它——它已經在第三格，沒有更上面可去。**
（只有純粹「檔案在那裡」的第二格通知不受影響。）

**這一節不得刪除，理由是升級規則會漏判。** 那條規則有兩個觸發條件（含技術符號、超過長度），
**兩個都可能漏**——判斷的是人（或 agent），不是一個會擋下來的程式。
⚠️ **而兩個條件漏判之後的處境不同**：字元那個漏了，下面三個機制還會擋；
**長度那個漏了，這一節擋不住**（三個機制全部看字元，不看長度）——那一格**目前沒有任何東西在守**。
⚠️ **縮小適用範圍不等於刪除。** 覆核時要分得出這兩者：範圍變小了，守衛還在。

| # | 機制 | 觸發 | 靜默嗎 |
|---|---|---|---|
| 1 | 指令代換 | 反引號、`$( )` | **是**——內容被當指令執行，結果代換進去（通常是空） |
| 2 | history expansion | `!` 後接非空白（`!53` 這種 MR 編號最常見） | **是**——整段被代換成空字串 |
| 3 | heredoc 提前結束 | 內文出現字面的 delimiter | **否**——指令會爆掉 |

⚠️ **反直覺的結論：會爆掉的那一種反而是最安全的。** 前兩種當天各出兩起，
**全部靠當事人在做別的事情時順手發現**；第三種立刻爆，一秒就知道。

**完整修法：**

1. **quoted heredoc**（`<<'…'`）——引號包住 delimiter 同時關掉機制 1 與 2（`set +H` 只關掉 2）：
   `read -r -d '' M <<'…' … ` 然後 `herdr agent prompt <name> "$M"`
2. **delimiter 挑一個不可能出現在內文的字串**——`EOF` 不算，寫技術訊息時很可能舉例用到它
3. **內容寫進檔案，通知只帶路徑**——內文完全不經過 shell。
   ⚠️ **不要寫成 `"$(cat file)"`**，理由有三個：整段內容**照樣灌進對方的 context**、
   檔案**沒有指定的落點與生命週期**、而且它把檔案當**傳輸手段**，與本協定的**檔案當載體**直接矛盾。
   **本協定要的是後者**——走 `msgs/`，通知只送路徑（見〈線與線之間的每一則往來都要選載體〉與附錄 B）。
   ⚠️ **不要說它「照樣經過 shell」——那句是假的。** command substitution 的**輸出不會被再次展開**，
   檔案裡的反引號不會被執行。
   > **這個形狀值得記：結論是對的，而支撐它的三個理由裡有一個是假的。**
   > **方向正確反而讓假理由更難被發現**——沒有人會去查一個自己同意的結論的每一條理由。
   > （2026-08-25 由跨模型覆核抓到，本檔五個同家族 lens 全數漏掉。）
   ⚠️ 這一條實際上已經被升級規則接走了：含這些字元的內容**本來就該升到第三格**。
   留著它是為了漏判的那一次。

> **2026-08-21 三起，同一天。** 一則回報裡的 memory 名稱與 commit hash 兩個都被吃掉，
> 收訊方看到的是「memory ⚠ 的 ⚠ 從…」與「已折進 #106（）」——**丟掉的正好是協調訊息裡
> 資訊密度最高、也最無法從上下文重建的兩種東西。**
> 協調者在寫「怎麼避免被 shell 吃字」那則廣播時**自己被第 3 種吃了**。
>
> ⚠️ **危險的不是缺一句，是那段內容被當成程式執行了。**
> **缺字是它留下的痕跡**——如果那段內容剛好是一個有效且有副作用的指令，就沒有痕跡。

> **訊息送達 ≠ 訊息完整。收訊方無法區分「他本來就沒寫」與「寫了但被吃掉」。**
> 若沒發現，收訊方會拿著一個不存在的名稱去 grep，得到「找不到」而不是「訊息壞了」
> ——**一個傳輸缺陷會被誤判成內容缺陷。**

**掃描要找空白**：`grep -nE '（ |「 |、 '` 之類——**被吃掉的痕跡是空白不是錯字。**

**不要叫一條線在自己的 pane 裡打互動指令做實驗。** 那會把輸入注進它正在跑的回合、
打斷它，而且結果要靠它事後描述，證據力比直接查文件弱。
（2026-08-21 實例：協調者要求在 pane 裡實測一個改名指令，該線拒絕並改用查證途徑——**那是對的**。）

**按鍵行為依「你正在驅動的那個 pane」的 TUI 而定，不是依你自己跑在哪個 agent 上。**
所以下面是一張對照表，不是一段條件文字：

| pane 的 kind | 按鍵 |
|---|---|
| `claude` | **不要送方向鍵**——`left` 會打開 background agents 側欄。**單題選單**可以 `↑/↓` ＋ `enter`；**多題選單一律不按鍵**（`tab`／方向鍵不會如預期換題，`enter` 會跳到 Submit **送出一份沒答完的答案**）。做法：`esc` 掉，改用**文字**回答每一題 |
| 其餘 kind | **本檔不假設。** 一律用**文字**回答，不要送方向鍵——送錯的代價（打斷回合、送出沒答完的答案）遠高於多打幾個字 |

## 附錄 B：開線與命名

### 判斷兩個 agent 在不在同一個 repo

**判準是「同一個 repo 的工作樹範圍內」**（主體〈兩道檢查〉）。取值：

⚠️ **而且要拿*對方的* cwd 去算，不是在你自己的目錄下跑一次。**
少了 `-C`，你算的是自己的 common dir，然後跟自己比——**這道守衛就什麼都沒守到**：

```bash
mine=$(realpath "$(git rev-parse --path-format=absolute --git-common-dir)")
theirs=$(realpath "$(git -C "<那個 agent 的 cwd>" rev-parse --path-format=absolute --git-common-dir)")
[ "$mine" = "$theirs" ]
```

⚠️ **三個字都不能少，而且錯了不會報錯：**

| 寫法 | 從 repo root | 從子目錄 |
|---|---|---|
| `git rev-parse --git-common-dir` | `.git` | `../.git` <!-- flag-order: demonstration of the flagless output, not a recipe --> |
| 旗標**置後**(`--git-common-dir --path-format=absolute`) | `.git` | `../.git` |
| 旗標**置前**(上面那道) | 絕對路徑 | 絕對路徑 |

`--path-format` **只影響它後面的選項**，置後**靜默無效且 exit code 為 0**。
寫錯的後果不是報錯，是**另一個 worktree 上合法的協調者被判成別的 repo**——
於是這道守衛變成通訊中斷，而 worktree 正是這套規則要支援的佈局。

**艦隊的產物落在 `~/.agent/fleets/<repo-slug>/<fleet>/`**，裡面兩個檔加一個目錄：
`fleet.md`（名冊）、`map.md`，與 **`msgs/`（線間訊息，一則一檔）**。

**`<repo-slug>` 跟 handoff 家族那一派**：絕對路徑裡的 `:`、`\`、`/`、`.` **四個字元都換成 `-`**。
理由是收線時 `msgs/` 的搬移目的地正是 `~/.agent/handoffs/<repo-slug>/attachments/`——
**兩者不同派就互相找不到**，而那個搬移是這條協定唯一的長命出口。

⚠️ **不要寫成「與 handoff、workflow 狀態同一個 key」——那是假的。**
`~/.agent/reference/repo-identity.md` 明文記著 slugify **尚未收斂成一派**：
auto-memory 與 local-files 只換 `/`，handoff 家族換四個。**新機制不得假設兩派產生同一個 key**，
要選一派並說明理由。
⚠️ **失敗形狀**：路徑含點的 repo 上，兩個協調者會導出**不同的 `<fleet>` 目錄**——
於是交接看起來像「沒有名冊、也沒有訊息」，**而兩者都寫成功了**，只是在另一個 key 底下，且 grep 不到。
**不要跟 `active_workflows.md` 混放**：那份檔案跨越所有艦隊、**沒有艦隊時也照樣存在**，
而名冊、map 與 `msgs/` 都與艦隊同生同滅。混放會讓拆艦隊變成「小心翼翼刪二留一」；
分開之後，**拆艦隊就是刪掉一個目錄**。

**`msgs/` 的檔名：`<ts>-<from>-<to>-<topic>.md`，而 `<topic>` 限 `[a-z0-9-]+`。**
一則訊息一個新檔——**動作是建檔，不是覆寫、也不是 append**
（理由見〈線與線之間的每一則往來都要選載體〉）。

⚠️ **字元集不是潔癖，它是這條協定最後一個暴露在 shell 的介面。**
`msgs/…-fix-!53-conflict.md` 這種檔名——`!53` 正是附錄 A 機制 2 最常見的觸發——
通知送出時會被吃成空字串，對方拿到一個**不存在的路徑**。
而**檔案確實存在**，所以對方最合理的結論是「協調者宣稱寫了一個沒寫的檔」。
**你這端 exit 0，沒有回執，沒有人會發現。**
⚠️ 「訊息只帶路徑就沒有那些字元」這句話，**只有在路徑的每一個元件各自受約束時才成立**——
而 `<topic>` 只是其中一個：

| 元件 | 約束 |
|---|---|
| `<ts>` | `YYYYMMDD-HHMMSS`（上一輪完全沒定，等於沒有約束） |
| `<from>`／`<to>` | herdr 名字本來就限 `[a-z][a-z0-9_-]{0,31}` |
| `<topic>` | `[a-z0-9-]+` |
| `<repo-slug>` | 由所選 slug 派別的轉換保證——⚠️ **它保證的是分隔符，不是 `$`、反引號、空格** |

**最後一道是機械的**：送出前把整個路徑用**單引號**包起來，不要靠上表逐格都沒漏。

⚠️ **不要落在 `~/.agent/handoffs/<repo-slug>/attachments/`。** 那個目錄綁 repo 不綁艦隊、
**沒有任何淘汰機制**（2026-08-25 實測某個 repo 底下 **117 個檔案**，五天內堆出來，
混著 `__pycache__`、`.bak-*`、腳本與凍結版本）。而線間訊息的量級**遠大於**協調者的交付物，
落進去等於加速淹沒——**而淹沒本身會讓「可重讀」變成「找不到」，正好消滅這條協定要買的那樣東西。**
那個目錄仍然是**協調者交付物**的家（見〈交付物不要留在會消失的地方〉），兩者不要混。

⚠️ **`msgs/` 與艦隊同生同滅，所以要活過艦隊的東西必須在收線時搬出去**——見〈收尾〉那份清單。

⚠️ **開艦隊時那個目錄若已經存在，停下來。** 前綴只在**活著的 agent 之間**唯一，**不是跨時間唯一**——
整支艦隊異常關閉時目錄不會被刪，於是日後一支不相干的艦隊選到同一個前綴，
**會把前一支的名冊、map 與 `msgs/` 當成自己的**。
⚠️ **殘留的 `msgs/` 是三者裡最糟的一種**：新艦隊會把前一支的線間訊息**連同裁決**讀成自己的。
要嘛是接續這支艦隊，要嘛確認是殘留後清空，
**不要直接沿用**。

**名字要符合 herdr 的 `[a-z][a-z0-9_-]{0,31}` 且在活著的 agent 之間唯一。**
那個唯一性是**整台機器一個池**，所以慣例是**艦隊前綴 ＋ change 名稱**：
協調者叫 `<fleet>-coordinator`，線叫 `<fleet>-<change>`。理由見主體〈定址〉。

**開艦隊時選定 `<fleet>`，這是一個裁決，不是一個推導。**

- **不能由 repo 名推導**：上限 32 字元，`mms_product_grouping_api-coordinator` 是 **36**，塞不進去。
  任何「自動 slug ＋ 截斷」的方案都會讓兩個長 repo 名截成同一段——
  **那是把撞名從一個看得見的選擇，換成一個看不見的碰撞。**
- **算得出可用長度**：`-coordinator` 這個尾巴佔掉 12 個字元，所以 `<fleet>` **最長 20**。
  而線名是 `<fleet>-<change>`，change 名稱可用的是 `31 - len(<fleet>)` 個字元——
  艦隊前綴取得越長，你的 change 名字就越短。**在命名當下算，不要等 `agent start` 失敗才知道。**
- **選完查一次有沒有撞**：`herdr agent list` 看有沒有活著的 agent 以 `<fleet>-` 開頭。
  完全同名 herdr 會在 `agent start` 當下擋下，但**前綴撞而尾巴不同它不會擋**——那正是最難查的那種。
- **寫進 handoff 的〈本輪產生的裁決〉**，接班協調者繼承它，不重選。

**兩道指令，不是一道。** 派線與開接班協調者的差別不是「記得砍掉一段」——見主體〈第二種形狀〉：

```bash
# ① 派一條線：帶關閉發問管道的旗標（依線的 kind 而定，見下表）＋ 升級契約
herdr agent start <fleet>-<change> --kind <line-kind> --pane <pane-id> -- <關閉發問管道的旗標>

# ② 開接班協調者：不帶那個旗標。它是唯一該升級到真人的角色
herdr agent start <fleet>-coordinator --kind <coordinator-kind> --pane <pane-id>
```

⚠️ **協調者那一列在開艦隊時就建好，②(接班)不重寫它。**
那一列記的是**啟動形狀**（kind ＋ 角色 ＋ 該不該帶旗標），而形狀在交接時不得變
（見主體〈交接必須同形狀〉）——**所以交接時名冊一列都不用改**。

**開艦隊時要做的**：選定 `<fleet>` 之後、派出第一條線之前，**先在 `fleet.md` 寫下協調者自己那一列**
（名字 `<fleet>-coordinator`、kind、角色＝協調者、**不該帶旗標**）。
少了這一列，差集表第三列會把你自己判成「不屬於本艦隊」，而**協調者猝死將永遠不可偵測**。

**② 開接班協調者時不要動名冊**：形狀沒變，那一列就還是對的。
把接班人的 `cmdline` 原文補寫進去，就是在帳本裡塞一格會過期的鏡子。

（形狀那一格的家是名冊。**不要把形狀值抄一份到 handoff**——同一個事實兩處維護，其中一份遲早會是舊的。
交接文件要寫的是**一句指路**：「接班者要以名冊那一列的形狀開出來」，見主體〈交接必須同形狀〉。）

**`<coordinator-kind>` 與 `<line-kind>` 是兩個不同的值。** 前者是接班協調者要跑什麼，
後者是那條線要跑什麼——**兩道指令各有各的**，別把同一個佔位符抄過去。

**`<line-kind>` 是那條線要跑什麼，不是你在跑什麼。** 你派得出 21 種——
把它渲染成你自己的 kind 會讓「線跟我同種」變成預設值，而那是一個沒有人會去質疑的預設值。

**關掉那條線的發問管道**（必須連同升級契約一起給，見主體）：

**這一節依「線的 kind」而定，不是依你自己的 kind。** 你派得出 21 種 agent，
所以下面是一張對照表而不是一段條件文字——**你自己跑在哪個 agent 上，不影響某條線有沒有機械保障**。

| 線的 kind | 有沒有機械手段 | 做法 |
|---|---|---|
| `claude` | **有** | 啟動時加 `--disallowedTools AskUserQuestion` |
| 其餘 kind | **目前未知／多半沒有** | 只有 prompt 約束——升級契約照給，但線在技術上仍攔得到真人 |

```bash
herdr agent start <fleet>-<change> --kind claude --pane <pane-id> -- --disallowedTools AskUserQuestion
```

**這個旗標是啟動參數，不寫進任何設定檔**，隨 session 結束消失——那正是主體要的範圍。
Claude 的設定檔三層分別是使用者層 `~/.claude/settings.json`、專案層
`<repo>/.claude/settings.json`（進版控）、專案本機層 `<repo>/.claude/settings.local.json`，
主體那張表對應的就是這三層。

> **打錯字它會警告，但不會拒絕啟動。** 實測傳一個不存在的 tool 名，
> 它印出 `Permission deny rule "…" matches no known tool — check for typos.`
> **然後照常啟動，deny 規則靜靜失效，exit code 仍是 0。**
> 在這條 skill 指定的部署方式下——一個沒有人在盯的 pane——那一行警告捲過去就等於沒發生。
> **所以派完之後要驗一次那條線是不是真的沒有那個工具，不要只看有沒有報錯。**

至於別的 kind：**判準是「那個 agent 有沒有一個對應的、可以關掉的 tool」**，
不是「它的旗標能不能碰工具集」——例如 Codex 就有 `--search`、`--enable/--disable <FEATURE>`
這類確實會動到工具集的旗標，只是它沒有一個等價於 `AskUserQuestion` 的東西可關。
派新 kind 之前先自己查一次，不要照抄本表。

**名字有幾層，依「線的 kind」而定——又是同一個軸。** 你要設定的是**那條線**被看見的名字，
與你自己跑在哪個 agent 上無關。

| 線的 kind | 名字有幾層 |
|---|---|
| `claude` | **三層**，見下表 |
| 其餘 kind | **多半只有 herdr 定址名這一層。** 派新 kind 前自己查一次有沒有等價旗標，不要假設有、也不要假設沒有 |

`claude` 線的三層，**最容易搞錯的是第二層到不了手機**：

| | 設定方式 | 誰看得到 |
|---|---|---|
| **herdr 定址名** | `herdr agent rename <pane> <name>` | 只有 herdr（`agent list` 的 name 欄、`agent prompt <name>`） |
| **本機 display name** | `claude -n <name>`（啟動）或 `/rename <name>`（跑到一半也能改） | prompt box、`/resume` picker、terminal title——**全部都是本機終端機** |
| **Remote Control session 名** | `claude --remote-control [name]` | **claude.ai 與手機 app**（唯一到得了那裡的一層） |

⚠️ **三層是各自獨立設定的，下面那道一行三層同名的指令是便利，不是機制。**
少了 `-n` 只會失去**本機 display name**，**不會失去定址名**——
實測一個 bare `claude`（無 `-n`、無 `--remote-control`）在 herdr 清單裡仍然有名字，
**因為定址名來自 `agent rename`。** 這一對最容易被讀成同一層。

開一條 `claude` 線時，一行讓三層同名：

```bash
herdr agent start <fleet>-<change> --kind claude --pane <pane-id> \
  -- --remote-control "<fleet>-<change>" -n "<fleet>-<change>"
```

herdr 把 `--` 之後的參數原樣透傳給 agent，於是同一個字串貫穿三層。
**前綴套的是那個字串本身**，所以三層自然一起帶著它——不需要為前綴再加任何機制。

**已經在跑的 session 補不了 `--remote-control`**（那是啟動旗標，橋接要在 session 建立時做）。
只能用 `/rename` 釘死本機那層，手機那層**從下一批新線開始**。

> **`--remote-control` 是行為改變，不只是加一個旗標**：session 會被橋接到 claude.ai，
> 對話內容、檔案路徑、程式碼片段都經過那邊。內部程式碼的專案要先確認這個代價可接受。

## 附錄 C：合併平台的行為

> 前提：repo 不保留 merge commit（fast-forward ＋ 一律 squash），且平台提供
> 「pipeline 成功後自動合併」。GitLab 的 `merge_method=ff` ＋ `squash_option=always` 是這種組合。

- **主線前進的那一刻，平台會「取消」已掛上的自動合併**，而不是保留著等你 rebase 完再繼續。
  所以每次 rebase 之後要**重掛一次，然後查一次確認它真的回來了**。那一次查是唯一該查的時點。
  > ⚠️ **常見的做錯法：輪詢 CI。** 平台支援自動合併就掛上去，剩下的交給它。
  > **上面那「查一次」是確認掛上了，不是恢復輪詢。**
- **force-push 之後，pipeline 狀態會有一段時間指著舊 commit 的成功紀錄。**
  判準要寫成兩件事而不是一件：**先確認 pipeline 指的 sha 對得上本地 HEAD，然後才看它的狀態**。
  順序不能反——狀態單獨看永遠有答案，而那個答案可能是上一輪的。
- **要查一個 MR/PR 為什麼合不進去，看平台的詳細合併狀態欄位。**
  陷阱：**Draft 狀態會蓋掉 CI 的阻擋原因**——是 Draft 時它一律回報 draft，即使 pipeline 是紅的
  也看不到 CI 的那一條。要驗證 CI 閘門有沒有生效，**必須先撤 Draft**。
