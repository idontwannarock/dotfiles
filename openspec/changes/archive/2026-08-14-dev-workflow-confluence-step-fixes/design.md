## Context

前一輪把判準、三態參數與退化行為都寫進了 spec，但共用 body 只被改了「新步驟出現在流程串哪個位置」與「新段落說了什麼」，**沒有回頭改被它依賴的舊段落**。於是 spec 描述的機制是完整的，body 描述的機制有兩個斷點。

這是一個可重複的失效形狀：新段落引用既有段落的行為（「step 2b 已經會讀 registry」），而那個引用**在寫下的當下是假的**——既有段落並不做那件事。斷點不會報錯，只會讓機制安靜地不運作。

## Goals / Non-Goals

**Goals:**

- 讓 body 描述的機制自洽且可執行：讀得到 `Doc Target`、寫得出第四欄、`none` 真的會短路。
- 消除 spec 與 body 內部四處互相矛盾的敘述。
- 減少 body 的重複敘述——它是每個 session 都載入的成本。

**Non-Goals:**

- 不改判準本身、不改掛點、不改三態語意——那些在前一輪已定案且 review 未提出異議。
- 不動兩端 name-map。
- 不修 registry 既有的欄名與 slug drift（延續前一輪的範圍決定）。

## Decisions

### D1. step 2b 同時補讀取與寫入，兩者缺一機制就不完整

2b 要改兩處：讀取清單加入 `Doc Target`，新列建立規則明示第四欄留空且此時不得詢問。

只補讀取會讓新 repo 永遠沒有第四欄可讀；只補寫入則讀取端仍不知道有這欄。兩者是同一個機制的兩半。

### D2. `none` 的短路寫在 body 段落開頭，不寫在結尾

短路條件放在段落**最前面**——讀到 `none` 就整段不必再讀。放結尾的話，模型已經套完判準、可能已經形成提案傾向才讀到「其實要跳過」，而指令的順序會影響它實際做了什麼。

### D3. 能力陳述句上移，擋在執行指令之前

前一輪把 `{{ .n.teamDocGap }}` 放在段落結尾，於是 Codex 端渲染出來的順序是「把它交給 `confluence-team-doc`」→（三段後）「本端根本沒有這個 skill」。指令先於它的否定條件，是與 D2 相同的錯誤形狀。

一般化：**在 agent 指令文件裡，條件與例外要寫在它所限制的指令之前**。這與程式碼的 guard clause 同構，理由也相同——讀者（模型）是循序執行的，讀到指令就可能開始做，後面的撤銷來不及。

### D4. 「停下」界定為停下這一步

`SHALL NOT 阻斷流程` 與退化時「說明後停下」的衝突，解法是明確界定：停的是團隊文件這一步，說明後繼續走 `finish-branch`。這與同份 spec 既有的「跨模型段不阻斷流程」是同一種處置，補一則對應 scenario 即可。

### D5. `none` 時此步驟為 no-op，而非「不執行此步驟」

三處無條件敘述（兩個流程 requirement 的 prose、`Review 通過` scenario）與 `none` 跳過的衝突，解法選擇改**被引用的那一端**：把 `none` 定義成此步驟的 no-op 結果，而不是把三處都加上例外條件。

理由是規則寫一處：例外寫在擁有該步驟的 requirement 裡，三個呼叫點就不必各自複製一份條件。

### D6. 內容邊界只留一份

body 內 `specs/` / `design.md` / `context/` 三格的敘述出現兩次（team-doc 段落一次、evergreen promotion 段落一次）。保留 evergreen promotion 那份（它本來就在談載體邊界），team-doc 段落改為指向它。

## Risks / Trade-offs

- **改 step 2b 會動到與本 change 無關的既有段落** → 這是必要的：新段落對它的引用在前一輪就已經是假的，不改就是留一個假陳述。改動限縮在補上第四欄的讀與寫，不重寫該段其他內容。
- **壓縮 body 段落可能刪掉模型真的需要的規則** → 每一處壓縮只刪重複的理由句與已在別處敘述的內容，不刪任何 SHALL 級的行為規則；壓縮後對照 spec 逐條確認規則仍有對應句子。
- **spec 空行風格統一是純美觀改動** → 範圍極小且限於本 change 前一輪新增的段落，不擴及全檔。
