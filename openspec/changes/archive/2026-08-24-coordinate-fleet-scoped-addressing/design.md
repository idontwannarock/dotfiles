## Context

`coordinate` 的定址規則建立在一個未被檢驗的前提上:「`coordinator` 這個名字指的是我這支艦隊的協調者」。
量到的事實推翻了它:

| 事實 | 來源 | 後果 |
|---|---|---|
| agent 名稱是整台機器一個扁平命名空間 | `herdr agent list` 一次回傳所有 workspace 的 agent | 兩個 repo 的艦隊共用同一個名稱池 |
| 名稱在活著的 agent 之間必須唯一 | `~/.claude/skills/herdr/SKILL.md:56` | 第二支艦隊搶不到 `coordinator` |
| 名字跟著 pane 佔用者走,agent 退場即釋放 | 同上 | 名字會**易主**,舊線的回報跟著改道 |
| 每筆 agent 都帶 `cwd` / `foreground_cwd` | `agent list` JSON | 歸屬有現成的機械判準 |
| **`herdr agent` 沒有任何 history 子命令** | `herdr agent` 子命令列表 | **已死的 session 與從未存在的 session 完全無法區分** |
| **`agent list` 沒有 context 用量欄位** | 同上(15 個欄位全數檢視) | 協調者看不到任何線的餘裕;只有線自己看得到 |

缺陷的形狀是**靜默投遞到真實但錯誤的收件人**——唯一性保證名字一定解得開,所以投遞端不會報錯,
收訊端看到的是一則格式正確、署名正確的回報。這正是 spec 既有的〈誰有資格說這句話〉那一族
(`discipline-skills:321`)的新成員:**下游分辨不出來**。

真正的發射點在**線側**:線讀的是 `dev-workflow` 的線側契約(body `:193`),不是 `coordinate`。

## Goals / Non-Goals

**Goals:**
- 同一台機器上多支艦隊並行時,線的回報只到得了自己的協調者
- 派線訊息漏給位址或位址已過期時,有一個機械後盾攔下誤投
- 前綴這個決定能跨換手存活(協調者一天換手八次以上)
- **艦隊的成員可以被掃出來**:漏掉的、被關掉的線要能被發現並重開

**Non-Goals:**
- 不改 herdr 的命名空間或唯一性語意——那是上游行為,本 skill 只能在其上建慣例
- **不做自動交接**(門檻、split pane 協定、接班人如何自證接住)——另一輪,它建立在本輪的名冊之上
- **不做多層載體導航索引**——另一輪,且見 D9 的命名前置條件
- 不追溯修正已經在跑的線;既有 session 靠 cwd 驗證兜住,新慣例從下一批線開始

## Decisions

### D1:前綴套到協調者**與**線,不只協調者

`<fleet>-coordinator` 與 `<fleet>-<change>`。

**替代方案**:只給協調者加前綴,線名維持 change 名稱。否決理由是線名撞名是同一個缺陷的另一個入口——
兩個 repo 各有一條 `fix-login`,第二條開不起來(唯一性)或協調者的 `agent prompt fix-login` 打到別人。
既然是同一個根因,一次收乾淨。

### D2:前綴由人在開艦隊時選定,不由 repo 路徑推導

**這是硬約束逼出來的,不是偏好**:名稱受 `[a-z][a-z0-9_-]{0,31}`,
`mms_product_grouping_api-coordinator` 是 36 字元,推導必然溢位。任何「自動 slug 化」的方案都要再配一套截斷規則,
而截斷會讓兩個長 repo 名撞在一起——**把撞名從一個看得見的選擇變成一個看不見的碰撞**。

代價:多一個開艦隊時要做的決定。緩解:它是**裁決**,有現成的載體與繼承機制(見 D3)。

<!-- evergreen-candidate -->
**判準**:一個識別碼若受長度上限約束而無法由來源推導,它就是一個決定,必須有人選、有地方記、有人繼承;
自動推導 + 截斷會把撞名從顯性選擇降級為隱性碰撞。

### D3(本輪修訂過一次):落檔的界線是「鏡子 vs 帳本」,不是「落不落檔」

**初版寫的是「不建任何機器層艦隊名冊」,那個範圍錯了。** 修正後的判準:

| 資料 | herdr 答不答得出 | 處置 |
|---|---|---|
| name / kind / pane / status / cwd(當下) | **答得出,且永遠是當下的** | **不落檔**。抄了就是〈複寫了別處的事實〉(`coordinate:167` 有實例) |
| 前綴這個決定 | 答不出 | handoff〈本輪產生的裁決〉 |
| 各 session 的 argv ＋ 角色 | 答不出(pane 一關即消失) | 名冊 |
| **「這條線該存在」** | **答不出。herdr 只列活著的** | **名冊** |

**推翻初版的關鍵事實**:`herdr agent` 沒有 history 子命令,名字在 agent 退出時被清除。
所以 **herdr 沒有「應該在」這個概念,只有「在」;缺席在它眼裡永遠不是異常**。
「協調者交接後漏掉一條當時剛好沒事的線」這個實際症狀,herdr 結構上答不了。

**名冊之所以不會過期,是因為它只記「session 被換掉時不會變的東西」**:
名字、kind、**指派的工作樹**、開線旗標與角色、這條線是幹嘛的。凡是會變的(pane、status、跑到第幾步、第幾任)一律不進去。

⚠️ **`cwd` 不屬於那一類,這是 cross-model review 抓到的**(2026-08-24)。
`docs/herdr.md:135-139`:**herdr 存的是 pane 的當下 cwd,跟著 `cd` 走**,不是建立時的;
而線可能從主 checkout 起手、之後才開 worktree。拿過期的 cwd 重開,
**會在錯的工作樹上開出一條名字完全正常的線**。
⇒ 名冊記的是**指派的工作樹(不可變)**,不是觀測到的 cwd;重開前 SHALL 再與 `active_workflows.md`
的 Path 欄核對一次(那一欄是那條線自己維護的當前落點)。
因此它與 herdr 不是兩套命名系統——**名冊答「該有哪些名字」,herdr 答「現在誰持有這個名字」**,
兩個問題不重疊,交接時只有後者變。**兩者的差集就是偵測器**:

| 名冊有 | herdr 有 | 判讀 |
|---|---|---|
| ✅ | ✅ | 正常 |
| ✅ | ❌ | **漏掉了／被關掉了** → 拿名冊上的 cwd ＋ kind ＋ 旗標原地重開 |
| ❌ | ✅ | 不屬於本艦隊(即 `:696` 那個「第三態」) |

第三列順帶補掉「三態使分母不可知」的一半:**分母不可知是因為沒有分子,名冊就是分子。**

**寫入風險幾乎為零**:線自我交接時名字不變,**名冊一列都不用改**。
寫入只發生在派線(協調者寫一列)與收尾(刪一列),沒有並行 append,避開〈共寫檔〉整族。

<!-- evergreen-candidate -->
**判準**:一份資料該不該落檔,先問「有沒有一個更新的權威來源」。有,就別鏡像它。
但**「查得到現在」不等於「查得到應該」**——只列活體的來源答不出缺席,那一格必須自己記。

### D4:前綴與 cwd 是兩道**正交**檢查;位址由派線訊息帶來

初稿把 cwd 說成艦隊歸屬的判準,不準確。實際上:

| 檢查 | 分得出什麼 |
|---|---|
| **前綴**(`<fleet>-`) | **哪一支艦隊**——在同一個 repo 內也分得出 |
| **cwd** | **哪一個 repo** |

⚠️ **cwd 比對的指令有一個靜默陷阱**(cross-model review 提出,實測確認比其所述更糟):
`git rev-parse --git-common-dir` 回傳 **cwd 相對路徑**(`.git`／`../.git`);
而 `--path-format=absolute` **只影響它後面的選項**——放在後面**靜默無效且 exit 0**。
⇒ 唯一正確的寫法是旗標在前並外包 `realpath`:
`realpath "$(git rev-parse --path-format=absolute --git-common-dir)"`。
寫錯的後果不是報錯,是**另一個 worktree 上合法的協調者被判成別的 repo**,
於是這道守衛變成通訊中斷——而 worktree 正是本 change 明說要支援的佈局。

線不讀協調者的 handoff,所以位址必須隨派線訊息送達——與升級契約同一則(沿用既有的
「關發問管道必須與升級契約同時給」的形狀)。訊息裡沒給位址 = 派線壞了,線 SHALL NOT 自行猜 `coordinator`,
要當作 fog 回報。cwd 驗證擺在**投遞前**與**收報時**兩端。

### D5:三層命名一併套前綴

既有〈命名三層各自獨立〉不變。前綴套在**同一個字串**上,
於是附錄 B 那道一行三層同名的指令自然帶著前綴,不需要新的機制。

### D6:艦隊產物落在 `~/.agent/fleets/<repo-slug>/<fleet>/`

**目錄邊界跟著生命週期與所有權走,不是跟著「哪裡已經有一棵樹」走。**

| 檔案 | 生命週期 | 沒有艦隊時 |
|---|---|---|
| `active_workflows.md` | per-repo,跨所有艦隊 | **照樣存在**(單人作業也寫) |
| `map.md` / `fleet.md` | **與艦隊同生同滅** | 不該存在 |

**替代方案**:放 `~/.agent/workflows/<slug>/`(與 `active_workflows.md` 同層)。否決理由有二:
一是 map 明文寫著「一條線自己的狀態指回 `active_workflows.md`」——它站在 workflow **之上**,
塞進 `workflows/` 是降一層,目錄名會說謊;二是混合生命週期會讓拆艦隊變成「小心翼翼刪二留一」,
分開之後拆艦隊就是刪一個目錄。

slug 用 `~/.agent/reference/repo-identity.md` 的正典定義,與 `handoffs/`、`workflows/` 同一個,
**不新增 slug 家族**。`<fleet>` 那一段就是名字前綴本身,名冊天然按艦隊分檔。

⚠️ **前綴只在「活著的 agent 之間」唯一,不是跨時間唯一**(cross-model review 提出的窄版)。
正常拆艦隊會刪掉目錄,但**整支艦隊異常關閉時不會**,於是日後一支不相干的艦隊選到同一個前綴,
會把前一支的 `fleet.md` 與 `map.md` 當成自己的。
⇒ 開艦隊時目錄若已存在,SHALL 停下來要求裁決(接續這支艦隊,或確認是殘留後清空),
SHALL NOT 直接沿用。

### D7:不變量寫在資源那一層,不是 repo 那一層

**一支艦隊必須完整擁有它所仲裁的稀缺資源池;兩支艦隊 SHALL NOT 共用同一個池。**

**「一個 repo 一支艦隊」不是公理,是這條在常見情況下的推論**,因為常見情況下 repo 就是資源池的邊界。
初稿把它寫成公理,而且是從機制(cwd 分不出同 repo 兩支)反推出來的——**那個因果是反的**,
而且事實上機制沒有這個限制:前綴那道就分得出來(見 D4)。

真正的理由在 domain:協調者存在的意義是仲裁稀缺資源,而合併位、migration 版號、編號區間、
`active_workflows.md`、影響半徑重疊的檔案**全部綁 repo**。map 的資源佔用登記處明文是**互斥**格。
**兩支艦隊共用一個池 ＝ 兩個仲裁者管同一批號碼 ＝ 沒有人在仲裁**,而且兩邊各自的登記處都會顯示「乾淨」,
因為它們互相看不見——與 8／7／10 那個合併值案例同一個形狀:**兩份都對,合起來錯。**

**真實的例外**:兩支艦隊打不同的 base branch(一支 `main`、一支長期 release 分支),合併位就是兩個池。
⚠️ 但 **base branch 分開不代表整個池分開**——migration 版號通常仍是同一條全域遞增序列。
所以判準要**逐項**問「這一項資源,兩支艦隊會不會爭」,不能整包判。

<!-- evergreen-candidate -->
**判準**:限制要寫在它真正的成因那一層。從實作機制反推出來的限制,會在機制改變時無聲失效,
而且答不出合法的例外——寫在成因層的規則答得出。

### D8:map 是 machine-project 層的工作面,不是 project 層的知識

wayfinder 的 map issue 是**一個 feature 的 issue**,做完就關掉,本來就不是長青知識。
本 skill 的 `map` 同層:per-repo、不進版控、與艦隊同生同滅。

**`map` 的內容不該升到 `context/`**——「Ａ 線現在卡在 Ｂ 線」是小時級變動,
放進要走 PR review 的長青 bundle 會在第一天腐爛。**工作面會死,殘留的原則不會死,兩者不該同層。**
durable 的殘留走既有的晉升閘門(evergreen-candidate → `context/`),與 `design.md` 同一條路。

**順帶修掉一個既有斷點**:開頭的對齊表寫「wayfinder map issue → handoff 檔」,
但 `:150` 又定義了另一個 `map`。**同一份文件裡「map」有兩個意思。**
實情是 wayfinder 的單一物件在這裡**裂成兩個**,因為多線引入了 wayfinder 沒有的拓撲,
而拓撲不屬於任何一個 session,塞不進任何一份 handoff。對齊表那一列要據實改寫。

### D9(僅記錄,不在本輪實作):第三個「map」不得沿用這個名字

日後若要做多層載體導航索引,**它不能叫 map**。屆時同一個系統裡會有三個同名物件
(wayfinder 的 map issue、本 skill 的線間 map、導航索引),而本輪整輪修的就是
「位址沒有錨點會解析到真實但錯誤的目標」。**在它存在之前換名,成本是零。**

## Risks / Trade-offs

- **前綴自己也會撞**(兩支艦隊都選 `chat`)→ 開艦隊時查一次 `agent list` 有沒有 `<prefix>-` 開頭的活 agent;
  完全同名 herdr 在 `agent start` 當下會擋,**前綴撞而尾巴不同它不會擋**
- **32 字元上限被 `<fleet>-<change>` 吃掉** → 附錄 B 明寫上限與扣除,讓人在**命名當下**知道
- **cwd 不等於 repo**:worktree 佈局下線的 cwd 是 worktree 路徑 →
  以 `git rev-parse --git-common-dir` 為準,不是字串前綴比對
- **名冊會喊狼來了**:線正常收尾卻沒刪列 → 刪列掛進既有的收尾清單(四訊號 ＋ 第五項 ＋ 第六項)
- **名冊被當成狀態表**:有人會想加「跑到第幾步」→ spec 明文禁止,那是 `active_workflows.md` 的,
  抄了就是〈複寫了別處的事實〉
- **規則變多**:`coordinate` 已 1052 行 → 沿用既有做法,貼進〈定址〉與附錄 B,不另立新節
- ⚠️ **本 change 讓資源撞號更難被察覺**(cross-model review 提出,無人反對):
  艦隊限定定址使兩支艦隊的訊息不再交錯——**而那正是撞號原本唯一會露出來的地方**。
  隔離之後,兩邊各自的登記處都內部一致,衝突只在合併時才炸。
  ⇒ 這是 D7 的不變量從「最好有」升級為「必須有」的理由,要寫進 skill 而非只留在 design
- **`repo-identity.md` 的正典錨點寫法同樣有 D4 那個旗標順序問題**,目前靠外包的 `realpath` 救著 →
  **獨立的一支 change**,不在本輪範圍;本輪只確保新寫的指令正確
