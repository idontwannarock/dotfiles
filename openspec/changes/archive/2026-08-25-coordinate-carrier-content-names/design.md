## Context

三格載體協定於 PR #124 落地(`c4244db`)。同一輪立下的〈序號不得承重〉禁令明文限於**收尾清單**,
而三格自己用「第一格／第二格/第三格」建了約 40 處位置指涉,分布在
`coordinate.md`(~24)、`dev-workflow.md`(2,英文 `first/third kind`)、
`openspec/specs/discipline-skills/spec.md`(~12)、`context/principles.md`(1)。

那張載體表**沒有印任何編號或名字**,所以「第一格」連一個可對照的錨都沒有。

前一輪判可延後,cross-model 判 live defect。2026-08-25 使用者裁決:改內容命名。

## Goals / Non-Goals

**Goals:**

- 三格有**名字**,而名字印在表上
- 位置指涉不再靠人自律——有守衛擋
- `attachments/` 無淘汰機制的論證不再依賴一個會腐爛的計數

**Non-Goals:**

- **不改「文件四格」**(`specs/` / `design.md` / `context/` / `docs/`)。同字不同族。
- **不動歸檔區**。歸檔是歷史記錄,不改原句。
- **不改 5 行 / 500 字元這兩個門檻值**(見 Open Questions)。
- 不碰〈證據的資格〉四層與〈傳訊管道〉兩層的序號(見 D3)。

## Decisions

### D1:名字保留「格」字

`訊息格` / `檔案格` / `檔案＋通知格`,而不是 `訊息` / `檔案` / `檔案＋通知`。

理由是**可 grep**,不是美感。「訊息」與「檔案」在這份 skill 裡是極常見的普通名詞
(「寫成檔案」「發訊息」出現上百次),拿它們當專名會讓讀者分不出一句話指的是載體還是普通名詞,
而 (b) 那支守衛測試需要一個分得開的 token。

代價:「格」帶著表格隱喻。可接受——表格本來就在,而且新增的名字欄讓隱喻對得上。

⚠️ 表格第三列的原文是「檔案 ＋ **帶摘要的 prompt**」。命名為「檔案＋通知格」會與被命名者用詞不一致,
所以**表格那格的文字要同步改成「檔案 ＋ 通知」**,並在旁邊保留「帶摘要的 prompt」作為說明。
命名與被命名者用詞不一致,讀者就要多做一次對照,而那正是這次要消滅的東西。

英文側(`dev-workflow.md`)對應為 `the message carrier` / `the file carrier` /
`the file-plus-notice carrier`。

### D2:載體表加一欄印出名字

沒有這一欄,內容命名跟位置指涉一樣沒有錨——只是把「數第幾列」換成「猜哪個名字對哪列」。

### D3:(b) 的字元集是 `第N項` ＋ `第N格`,**不含「層」**

`〈證據的資格〉` 四層與 `〈送訊息〉` 兩層的序號**帶遞進語意**(第①層比第②層更基礎),
與收尾清單的純位置指涉不同族;而現行 spec 的禁令範圍本來就明文限於收尾清單。

⚠️ **前一輪 handoff 對這支測試的預測是錯的。** 它說首跑會在 `coordinate.md` 兩處紅、
「它們指向〈證據的資格〉那張四層表」。實測:照它給的 pattern(`第N項`)只紅**一處**
(`coordinate.md:606`,而那是規則自己舉的反例);四層表用的是「第①**層**」,`項` 抓不到。

換句話說,照 handoff 字面寫出來的 (b) 在改名完成後會是一支**永遠綠**的測試。
把「格」納入字元集正是讓它有真實母體的原因:改前 ~40 處紅,改後 0。

豁免 1 條:`coordinate.md:606`「不要寫『第五項』」——那是規則自述,是 mention 不是 use。

### D4:三支測試的母體含 `spec.md`,且 CI 觸發路徑要同步補

`spec.md` 是 SHALL 的正典。不守它等於守了副本放過正本。

⚠️ **母體與 CI 的 `paths:` 是兩份各自維護的清單,而它們必須是同一個集合。**
現行 `test-shell.yml` 只觸發 `home/.chezmoitemplates/skills/**`。把 `spec.md` 納入母體卻不改 `paths:`,
做出來的是一支只在「別的檔案被改」時才跑的測試——它對**只改 `spec.md` 的 PR** 永遠沉默,
而那正是唯一需要它出聲的 PR。這種錯法沒有任何測試抓得到,因為它就是測試本身。

<!-- evergreen-candidate -->
**守衛測試的母體宣告與 CI 的觸發路徑必須同時改。** 只改其中一邊做出來的是一支對它自己那類 PR 沉默的測試,
而沉默與通過在 CI 上長得一模一樣。

### D5:`117 檔案` 改結構性論證

現行論證:某 repo 底下 117 個檔案、五天。**那個數字證明不了那個結論**——
五天的窗證偽不了 30 天 TTL;而且數字會腐爛,讀者在別的機器上無法重驗。

改為:**handoff / pickup 工具鏈裡沒有任何東西會刪 `attachments/`**
(`pickup` 只把 handoff `mv` 進 `archive/`,不碰 attachments)。
這是結構性的,任何人在任何機器上讀那兩支 skill 就能重驗。

`spec.md` 那條本來就沒寫數字,是對的高度——所以 spec 側只補「論證 SHALL 為結構性」這條約束。

<!-- evergreen-candidate -->
**用觀測到的計數證明「沒有淘汰機制」是無效論證。** 一個有限的觀測窗證偽不了一個比它長的 TTL,
而計數會腐爛且在別的機器上無法重驗。要證明沒有淘汰機制,舉出**沒有任何程式碼路徑會刪它**。

### D6:同字不同族的兩處明文列為不動

`context/principles.md` 的「文件四格」與 `archive/2026-08-13-.../design.md:40` 的「第四格」
講的是 `specs/` / `design.md` / `context/` / `docs/`,與訊息載體無關。

一個預測式的 `sed -i 's/第三格/檔案＋通知格/g'` 會把前者改成胡言亂語,**而且不會有任何測試轉紅**
——那句話本來就沒有守衛。這是為什麼動工前先列舉母體再分類,而不是照 handoff 的估計數直接改。

## Risks / Trade-offs

- **(c) 那支同步測試會過度約束兩份 body** → 只比對門檻值與觸發字元集三者,不比對措辭。
  兩份是刻意複寫且用不同語言(中文/英文),比對措辭必然誤報。
- **(b) 不禁「層」留了一個洞**:未來想用位置指涉的人改寫「第三層」就逃掉了 →
  接受。現有「層」的用法全部指向真正分層的結構,而為一個沒有實例的風險擴大禁令,
  換來的是一份會不斷變長的豁免清單——長豁免清單本身就是「規則拓寬了」的徵兆。
- **改名觸及 ~40 處,漏改一處就是規則與內文不一致** → (b) 那支測試就是為此存在;
  驗收以測試轉綠為準,不以「我改完了」為準。
