## Context

`coordinate` v1 於 2026-08-21 隨 PR #106 進 chezmoi source，PR #107 補上派線契約。
凍結之後浮出來的教訓沒有地方可去，於是全部落在 coordinator 維護的
`coordinate-v2-backlog.md`（正本，**本 change 不另存副本**）。撰寫本 change 時該檔有 42 項編號（#37–42 是第四任 coordinator 在本 change 起草當下追加的，
回答的正是「還有什麼只在腦子裡」這一問），其中 #7 已隨 #106 落地、#32 已隨 #107 落地、
#30 被 #32 的 A/B 實測推翻，**實收 39 項**。

⚠️ **backlog 的維護者換過四手，每一手只寫得下自己看到的**——它不是「一份可能有遺漏的清單」，
是**四段不重疊的視野疊在一起**。所以本 change 把它當**證據集**而不是規格：
發現兩則其實同族、或某則的通則比它自己寫的更寬時直接改，改了什麼回報 coordinator。

約束：

- **分層判準沿用 v1**（已是 spec）：「換一個 repo、換一個 merge 平台、換一個 agent kind 之後，
  這句話會不會**靜默失效**」——會的進附錄並標明前提。帶日期的軼事留主體。
- **skill 內文不得以裸 slug 指向 repo-scoped memory**（已是 spec scenario）。
- **依「被派出的線的 kind」而定的事實，不得依讀者的 kind 條件化**（已是 spec scenario）。

## Goals / Non-Goals

**Goals**

- 把 33 項教訓放進**協調者實際會讀到的位置**，而不是留在待納入清單。
- 放置的分類軸是**失效的機制**，不是主題——同一個主題底下失效機制不同的東西要分開。
- 每條規則保留它的來源軼事（帶日期），因為那是它適用條件的唯一證據。

**Non-Goals**

- 不重寫 v1 已有的節；本輪是擴充與新增。
- 不動 `dev-workflow` 的線側契約（#107 已到位）。
- 不處理 backlog 明列「不收」的那幾項（`chezmoi apply` 字典序屬 `chezmoi-author`；
  deploy／公司環境事實屬各自 repo-scoped memory）。

## Decisions

### D1. 〈證據的資格〉獨立成節，不併進〈跨線事實〉

backlog #3 已把理由寫死：**分類軸是失效的機制，不是主題。**
〈跨線事實〉的失效是「**取到錯的值**」（8／7／10 都對，合併值是 9）；本族的失效是
「**這個東西根本不回答你的問題，而它的措辭聽起來像在回答**」。後者防不了的話，前面所有的合併都是在合併垃圾。

這一節收四層，且四層是**遞進**的，寫成清單而不是散文（#12 的教訓：寫在括號裡的規則在覆核時會被略讀）：

| 層 | 問題 | 防的漏 | 來源 |
|---|---|---|---|
| ① | 這個欄位對「是」與「否」兩種輸入會不會給出**不同**的答案？ | 顯示欄位沒資格當證據 | #3 |
| ② | 這個檢查在什麼情況下會紅？**做給我看** | 檢查根本不會紅 | #12 |
| ③ | 你注入的**真的是一個差異**嗎 | 示範本身是 no-op | #12 補充 |
| ④ | 它比的東西**涵蓋了交付物的全部**嗎 | 覆蓋範圍的漏（③最難，因為①②都會過） | #14 |

外加兩條同族但方向不同的：

- **紅燈的歸因**（#15）：探針要單獨改變你主張的那一個變因；順帶改變別的，紅燈就不再指向你的主張。
- **失敗的計數是完整性的證據**（#16）：恰好四支紅、其餘 443 綠，證的不只是那四處會錯，
  還證明其他 443 支都不會。驗收盤點時要問「**有沒有一個動作，它的結果會在你漏掉東西時不一樣**」。

以及 #18 的**機制**（當事人明確要求不要寫成「記得檢查探針」這種可以讀過去的告誡）：
動手前先問「**這個 repo 裡有誰會因為我這個探針而不高興**」——會不高興的東西就是探針的規格說明書；
「沒有人會不高興」不是安全訊號，是「沒有東西在守這一格」的訊號。

### D2. map 獨立成節，並明寫它**不是**第三個正本

wayfinder 的四格之外要加兩格，而且性質相反（#4）：**資源佔用登記處是互斥的**（誰佔了別人不能用），
**跨線量測是分歧的**（三個都對，要的是合併值）。混成一格的具體害處是「報了數字」會被當成「認領了」。

資源格至少三欄（配了什麼／目前用到哪／已回收）——少第三欄，沒用完的號段在線收工那一刻永久蒸發且 grep 不到。

寫入權要分開（理由是 v1 自己那節〈共寫檔〉：平行 append 永遠成功、沒有警告）：裁決欄只有協調者寫，
資源格的「目前用到哪／已回收」由線自己寫，量測原始值由線寫且註明站在哪個 commit 上量的，合併值由協調者寫且標明是合併值。

**節的前言要先講清楚 map 與另外兩個載體的分工**（#5、#6）：handoff 目錄答「有哪些事」、
`active_workflows.md` 答「誰跑到哪一步」、map 只答「這件事在哪、卡著誰、誰卡著它」。
一條線自己的狀態指回 `active_workflows.md`，抄進 map 就是〈複寫了別處的事實〉。

### D3. 結論重驗補的是**方向**，不是新節

v1〈不要照單全收下游的結論〉寫的三個實例全是「協調者 ← 線」。要補的是兩件事，都併進該節：

1. **後任 ← 前任**（#2）：交接是**唯一一次**有人帶著新鮮眼睛重讀前任全部結論的時刻，
   所以接手包含「重驗你要繼承的結論」。而且**難堪的結論更少人去查**——前任的「我搞砸了」也要重驗
   （#7 的軼事反轉已在附錄 A，這裡指回去，不重述）。
2. **否定斷言**（#31 + #31b）：`grep` 型的否定斷言（「零讀取端」「沒有別的 caller」「沒有人動這個檔」）
   對佇列裡開著的 MR 是隱形的。通則比佇列寬：**斷言一件事之前，先確認自己讀的是能回答它的那個東西**。
   協調者這一側要主動比對合併佇列，不要只採信。

`#10`（你是量的還是記的）與 `#13`（有沒有動某個檔案是查得到的事）是同一條規則的兩面，
放在〈跨線事實〉：#10 要求線去量，#13 是協調者自己用推論回答了一個該去查的問題，
而**協調者犯這個錯比線貴**——它的答案會被多條線當成跨線事實採信。

### D4. 「工具回報成功不等於做了事」不新開節，分散進它們各自的載體

#11（shell 吃 backtick）、#23（`str.replace()` 靜默 no-op）、#34 家族、#36（`--abort` 是空操作）
共同形狀相同：**下游的每一個檢查都會通過，只有把成品讀出來才看得到。**
但它們的**載體**不同，而讀者是在動那個載體時才需要那條規則：

- 傳訊那一族（#11、#34、34b、34c、34d）→ **附錄 A 的 `agent prompt` 節**，因為它是那道指令的使用前提。
- 改檔那一族（#23、#35）→ 主體〈共寫檔〉與〈整份覆寫之前先讀〉。
- git 那一條（#36）→ 附錄 C（合併平台行為）旁，因為它是 git 操作的前提。

共同的那句話（**症狀是空白不是錯字；工具回報成功、檔案真的被改了，只有讀回成品才看得到**）
寫進〈整份覆寫之前先讀〉的開頭，因為那一節已經是「這一族的失敗全部靜默」的所在地。

### D5. #35 的三層寫成階梯，並點名 map 自己是最該被治的病例

先讀（擋盲寫）→ 條件寫／`assert` 錨點（擋錨點消失）→ **只碰自己那一列**（擋別人新增）。
前兩層都不夠：`assert` 保護的是「我的錨點還在」，不是「這個檔案沒有被別人動過」。
退而求其次是記下 `mtime_ns` + `size` 並在寫入前重驗——**它不是第三層，但它把靜默還原變成一次中止**。

要點名的是：`MAP.md` 明寫「任何線都可以追加」，而它整場都是協調者在做整檔 read-modify-write。
**寫規則的人最容易在自己的規則上犯規**——v1 已經有這句話（用在 repo-bound 內容上），這裡是它的第二個病例。

### D6. 共寫資源不只是檔案

v1〈共寫檔〉列的三樣全是檔案。要補兩條性質更遠的：

- **`git checkout` 本身**（#25）：一樣共寫、一樣沒有警告、一樣靜默。
  規則：動共用 checkout 的 HEAD 前先查 `active_workflows.md` 有沒有別人佔著；自己有 worktree 就不要碰主 checkout。
- **一個工具讀取設定的位置**（#26）：dotfiles 的 chezmoi source 指向那個共用 checkout，
  於是「A 線正常地在自己 branch 工作」＋「B 線正常地合併 PR」**組合出第三個效果，而兩邊各自都看不見**。
  這比〈共寫檔〉更遠，所以放在該節末尾當作它的推廣。

<!-- evergreen-candidate -->
**共寫資源的判準不是「它是不是檔案」，是「有沒有第二個人的行為會透過它改變我的結果」。**

### D7. 收尾加第六項，且它與第五項同性質

第五項（編號回收）是「只能問、查不到」。第六項（#29）也是：**「還有什麼只有你知道？」**
四訊號量的是「產出有沒有落地」，未決事項是「有沒有問題還掛著」——**兩者可以同時為真**，
而只有線自己知道後者。實例：協調者關掉 `source-alias-mapping` 時四訊號全齊、產出全在檔案裡，
但它有一件未決（短通知的 A／B 版）就此失去主人。

#17（順手解掉的小坑要有住址）也掛這裡：小坑最容易被判定成「不值得寫下來」，
而它們正是重複成本最高的一類——每個新來的人都要付一次，每個人付的都不多。

### D8. 附錄 A 的輸入框判斷之前，先插一步機械檢查

v1 現在要協調者**判斷**那段文字是誰留的，而那個判斷 2026-08-21 讓一條線停了兩輪。
機械檢查在判斷之前（#24）：**先用 `--format ansi` 讀一次，帶 `ESC[2m`（dim）的是 placeholder ghost，
不在 buffer 裡，輸入框其實是空的。** 只有非 dim 的非空內容才需要進入「是誰留的」那張表。

這一步同時解掉 v1〈實例甲〉那個三方誤判——當時若有人用 `--format ansi` 讀一次，就不必猜。

### D9. 不新增 name-map 條目，而條件分支的軸要逐條判

本輪要加的 agent 專屬內容有兩處，**而它們的軸相反**——這正是 #33 那條 spec scenario 要防的：

| 內容 | 取決於誰 | 怎麼寫 |
|---|---|---|
| 輸入框的 dim placeholder | **被讀的那條線**的 TUI | **不做條件分支**——寫成無條件的機械檢查，並註明實測於哪一種 TUI |
| `SendMessage` 這條傳訊管道 | **協調者自己**的工具 | **做條件分支**（`{{ if eq .n.tool "claude" }}`）——Codex 端沒有等價機制，那節對它是「唯一的路」而非退路 |

起草初稿曾把第一列也放進 `{{ if eq .n.tool "claude" }}`，**那是同一個錯的軸**：
Claude 協調者讀 codex 線的畫面時仍然需要那個檢查，而 Codex 協調者讀 claude 線時會讀不到它。
不新增 name-map key。

### D10. 把 backlog 分散在四處的四則收成〈誰有資格說這句話〉一節

**這是本 change 對 backlog 分類的唯一一處改動**，理由是 backlog 自己第 3 項那條判準
（**分類軸是失效的機制，不是主題**）用在這四則上會得到與 backlog 不同的答案：

| backlog | 它建議的落點 | 實際的失效機制 |
|---|---|---|
| #1 該由誰說 | 〈交付物〉或新開一節（**未決的二選一**） | 一件該由當事人說的話被轉述了 |
| #28 轉述第三方 | 反模式 | A 的提醒被轉述成對 B 的指控 |
| #39 有一類授權連轉述都不夠 | 〈派線時關掉發問管道〉 | 使用者的權限決定被 peer 代答 |
| #41 選單回了使用者沒選過的答案 | 主體（未指定節） | **一個從未存在的裁決以使用者的名義生效** |

四則共用同一個失效機制：**一句話的署名跟它真正的來源對不上**，而**下游分辨不出來**
——收訊方看到的署名是對的、內容也通順。#41 是這一族的極端形態，也是唯一一個
「不是蓋掉別人已寫下的東西，而是憑空生出一個從未存在的決定」的形態。

**第四任 coordinator 的意見是「#1 獨立成節」，本 change 採納並擴大**：不是 #1 一則獨立，
是這一族獨立。#39 的**代價**要跟規則一起寫（否則它會與同一節的「關掉線的發問管道」互相咬死：
線問不到人、協調者又不能代答，那個 pane 就進入沒有出口的狀態），所以
〈派線時關掉線的發問管道〉那節保留一句指回本節——**解法是協調者把人帶到那個 pane，不是代答；
升級鏈的終點是人的鍵盤，不是協調者的複述。**

### D11. #38 的通則進〈證據的資格〉，機制留附錄 A

「`herdr agent read --source visible` 在 idle pane 上回傳過期快照」是工具行為，進附錄。
但它的通則不是：**一個永遠有答案的讀取，答案可能屬於上一個時刻。**
同族已知三個（`head_pipeline.sha` 要先比再看 status、`git status` 乾淨屬於「還沒被搬」那一刻、本則），
**三個載體不同、機制相同**，所以通則寫在〈證據的資格〉當第①層的孿生條：
①問的是「這個欄位分不分得出是與否」，這一條問的是「**這個答案屬於哪一個時刻**」。

### D12. #37 是把附錄 A 的 `agent prompt` 節**降級**，不是取代

`SendMessage` 結構上免疫於 #34 的三個吃字機制與 append 問題（JSON 參數、不經 shell、不碰輸入框），
**但可達性不是無條件的**——實測有送不到的對象，當天真的退回 `agent prompt` 一次。
所以附錄 A 加一張兩層表，而 `agent prompt` 那節**不刪**：它從日常做法變成退路的說明書，
而退路會用到。這一則本身就是 #12 那條「一個檢查在什麼情況下會紅」的反面
——**一個結構上更安全的管道，它的前提是「對方可達」，而那個前提會失敗。**

## Risks / Trade-offs

- **skill 長度**：v1 為 430 行，本輪實際 **+512 行（來到 942 行）**——比起草前估的 +200 多一倍以上，
  因為 backlog 在起草期間從 33 項長到 39 項，且每條規則都帶一則軼事（軼事留主體是既有 spec）。
  長到沒有人讀完就等於沒寫。
  → 緩解：新增內容一律用表格與清單，不用散文段落；每節開頭一句話講清楚它防的是哪一種失效。
  這同時是 #12 的規則（散文段落、括號、附註、引言在覆核時會被略讀）用在本檔自己身上。
- **backlog 仍在長**：撰寫期間 coordinator 隨時可能追加。
  → 緩解：正本是那個檔案，本 change **不複製**它；起草前主動問一次「還有什麼只在腦子裡」
  （#7 那格盲區：mtime 掃不到純對話裡的教訓）。
- **本輪納入的內容多半來自同一天、同一批線**：可能過度擬合當天的環境。
  → 緩解：分層判準本來就是為這件事設計的——會隨環境靜默失效的進附錄並標明前提。

## Migration Plan

1. 改 `home/.chezmoitemplates/skills/coordinate.md`（唯一的內容來源，兩個 wrapper 共讀）。
2. 兩個 wrapper 各 render 一次驗證：Claude 版與 Codex 版都要看，Codex 版不得出現 Claude 專屬旗標。
3. `chezmoi apply` **限縮**：`--source <本 worktree>/home` 並點名 target **目錄**（不要傳檔案；
   多 target 依字典序處理且失敗即中止其後全部）。主 checkout 此刻停在別條線的 branch，
   裸跑會把 skill 退回舊版。
4. `chezmoi status` 對四個 target 乾淨。
5. 回退：本 change 只動文件，`git revert` 即可；已 apply 的 target 重跑限縮 apply 覆蓋回去。
