## Context

PR #108 之後 946 行。使用者裁決「本輪不重排」後，本輪專做重排。
coordinator 的判準：**「一條線在動工前三十秒內，讀得到它要的那句話嗎？」**
它明確說「**不要砍軼事**」——帶時間戳的事實不是設定，v1 那個決定是對的。

## Goals / Non-Goals

**Goals**：每節首段就是該節的承重規則；軼事、動機、前提降到規則之後。

**Non-Goals**

- 不刪任何軼事、不刪任何規則。
- 不動附錄的分層判準。
- **不決定〈反模式〉的存廢**（見 Open Questions）。

## Decisions

### D1. 「承重規則」的定義要可判定，否則下一輪又會漂

> **一節的承重規則 = 讀者若只讀這一句，會不會做出正確的動作。**

不是「最重要的一句」（那是品味），是「**單獨讀它就足以改變行為**」。
動機（為什麼有這一節）、前提（什麼情況下適用）、軼事（怎麼知道的）**都不合格**
——它們單獨讀了都不會讓人做出動作。

### D2. 前提怎麼辦——降到規則之後，但不得刪

〈排程〉開頭四行前提是**必要**的（換一種 merge 設定，前兩條規則的急迫性就變了），
所以不能刪，也不能移進附錄（它綁的是規則本身不是平台機制）。
**做法：一句話的承重規則置頂，前提緊接其後，用引言標記包起來。**
讀者三十秒讀到規則，要判斷適不適用自己時再讀下一段。

### D3. 〈收尾〉補一個六項的清單置頂

目前四訊號是清單，第五、六項散在 60 行的散文與軼事之間。
**六項一次列完置頂**，並標明哪兩項是「只能問、查不到」；細節與軼事留在下面。
這也是 skill 自己那條規則（#12）用在自己身上：**寫在散文裡與寫在清單裡，
對讀者的效果不同，但對寫的人而言感覺一樣「已經寫了」。**

### D4. 這次不加守衛

「首段是不是承重規則」**沒有可機械化的判準**——`skill-name-map-axis.test.sh` 那條可以，
是因為「有沒有 `axis: reader` 標記」是形式問題。這一條是內容問題。
**照上一輪學到的：一個沒有標明母體的綠燈比沒有守衛更糟**，所以寫成 spec 由 review 把關，不假造機械檢查。

## Risks / Trade-offs

- **重排的 diff 難讀**（大段移動看起來像重寫）→ 緩解：每節一個 commit 段落，
  且 PR 描述點名「純移動」與「有改字」的分界；驗證用 `git diff --stat` 之外再比對**字數**是否守恆。
- **移動時把軼事與它證的規則拆散** → 緩解：移動後逐節重讀一次，軼事必須緊跟在它支持的那條規則下面。
